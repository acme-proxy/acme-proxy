# CLAUDE.md — `tests/`

The harness and the suites that drive the app from outside. The repository-wide file (`../CLAUDE.md`) holds the nextest and `ENV_LOCK` rules that apply everywhere, the commands and CI; `src/CLAUDE.md` holds the design each suite exercises and the inline unit tests that sit beside the code.

`cargo nextest run` runs the suite. Tests use an in-memory SQLite (`Database::connect_in_memory()`) and an in-memory local CA (`LocalCa::generate_in_memory`), so no *shared* state outlives a test.

Four suites do touch the disk or a loopback socket, each for a reason worth stating rather than leaving as an apparent exception: `reload.rs` writes a `config.toml` and binds two ephemeral ports (a reload re-reads the file, so there is nothing to fake); `filters.rs` runs the IPAM mocks on loopback and, with `custom_signer.rs`, writes and execs scripts (which is *why* nextest is required — see the `ETXTBSY` note below); and `templating.rs`'s loader tests write a template to a `TempDir`. **Nothing reaches a real network.**

**nextest is required, not preferred.** The `custom` script tests in `signer`/`filter`/`notify` exec a file they just wrote; under plain `cargo test`, which runs tests as threads of one process, that intermittently fails `ETXTBSY` — another thread's `Command::spawn` forks while the file's write descriptor is still open, and the forked child holds it until its own exec. Nothing in the test can avoid this (the kernel checks the inode, so writing elsewhere and renaming into place does not help), so `cargo test --lib` fails roughly one run in three. nextest's process-per-test isolation removes it entirely.

Anything calling `Config::load()` in a test must hold `config::ENV_LOCK` (crate-wide, `#[cfg(test)]`, in `src/config/mod.rs`) — `ACME_PROXY_*`/`ACME_PROXY_CONFIG` are process state, so a test setting one while another loads makes the second read the first's variables. One lock for the whole crate on purpose: per-module locks serialise a module against itself and nothing else.

## Harness

`tests/common/mod.rs`: `test_app_full` is the single place the app is built — one profile named `default` through the real `build_app`, so paths carry the endpoint prefix (exports `HOST`, `PROFILE`/`PREFIX`/`BASE`, and `p("/newOrder")`). Variants: `test_app_with_db` (exposes the `Arc<Database>` so a test can close its pool), `test_app_with_signer`/`_filter`/`_challenges`, `test_app_with_profiles` + `TestProfile`. Because `oneshot` has no socket, `send_from`/`post_from`/`fetch_nonce_from` insert the `ConnectInfo<SocketAddr>` extension by hand — that is how a test gives filters a client address. Web admin: `admin_config()`, `test_admin_app`/`test_admin_app_with_signer` (the latter for tests that must genuinely *issue* before revoking), `test_admin_app_logged_in` → `AdminSessionHandle { cookie, csrf }`, plus `admin_request`/`admin_login`/`session_cookie_token`/`json_body`. `test_admin_app` and `test_app_full` share `one_profile`, so the two cannot drift into mounting different endpoints. Both test signers (`EcSigner`, `RsaSigner`) implement `TestSigner` (`sign`/`sign_kid`/`sign_kid_empty` as default methods) — **import it wherever you call `signer.sign(...)`**. `build_jws`/`build_jws_kid`/`build_jws_kid_empty` and the lower-level `jwk()`/`sign_input()`/`flattened_jws()` are `pub` for crafting off-nominal envelopes. `common::acme` is the ACME ladder itself — `post`, `register`, `new_order`, `drive_to_ready`, `ready_order`, `finalize`, `issue_certificate`, `post_as_get`, `trigger`, `path_of`, and `assert_problem`/`assert_problem_detail`. Nineteen suites had each grown their own copy (`post` in twenty-two files, `register` in eighteen); use these rather than writing a twentieth. **Assert with `assert_problem`, not a bare status**: a refusal that keeps its status and changes its `type` is a different answer to the client, and `unauthorized` and `rejectedIdentifier` are both `403`. Other fixtures: `make_csr`/`make_csr_with_sans`/`make_csr_and_keypair`, `first_certificate`, `FailingSigner`, `RejectingFilter`, `StubValidator`, `RecordingValidator`, the `*_challenges` registry builders.

## Integration tests

One line each (`tests/*.rs`, driving `build_router` via `tower::ServiceExt::oneshot`):

- `basic_endpoints.rs` — health/directory/newNonce/redirect, the `Replay-Nonce` middleware, POST-as-GET on directory/newNonce (§6.3), the 405/404 problem documents, the `Link: rel="index"` layer.
- `new_account.rs` — the full newNonce→newAccount lifecycle, EC + RSA, nonce replay.
- `jws_rejections.rs` — the extractor's rejection branches, table-driven, plus the `415` media-type check and `badSignatureAlgorithm`'s `algorithms` list.
- `accounts.rs` / `update_account.rs` — signed read, contact update, deactivation, cross-account rejection, and §7.1.2.1 orders-list filtering (expired/`invalid` omitted, a `valid` order kept past its own `expires`).
- `contacts.rs` — `mailto:` contact validation (§7.3): scheme → `unsupportedContact`, `hfields`/multiple addresses → `invalidContact`, on both `newAccount` and the update path.
- `authz_deactivation.rs` — §7.5.2: the deactivation payload, the read path beside it, order demotion, and the two refusals (already-issued order, non-owner).
- `replaces.rs` — RFC 9773 §5: reflection on the 201 *and* later polls, the three correspondence checks, `409 alreadyReplaced`, an `invalid` replacement not blocking a retry.
- `directory_meta.rs` — the `[meta]` keys in the directory, and §7.3.3's terms-of-service requirement (the second crate using a non-default `Config`).
- `orders.rs` — the full order→certificate lifecycle (EC + RSA), multi-identifier orders, finalize/ownership rejections.
- `db_failures.rs` — a closed pool → `serverInternal` across the request paths that write: the extractor's nonce check and `kid` lookup, `newOrder` persistence, the nonce middleware, a challenge trigger, an authorization deactivation, `keyChange`, certificate retrieval and the RFC 9773 `replaces` lookup. Deliberately **not** every write path — the pool is closed before the request, so a failure *between* two writes needs a fixture of its own (`RevokePersistFailingSigner`, in `revoke_cert.rs`).
- `admission.rs` — `[server]`'s admission control on the ACME routes: `max_concurrent_requests` and `admission_wait_ms` shedding rather than queueing (a `503` carrying `Retry-After`), `request_timeout_ms`, and `max_body_bytes`. `GET /health` is mounted outside all of it, which is why nothing needs exempting for a health probe.
- `filters.rs` — the filter subsystem through the real router, incl. spoofed XFF, CSR-smuggled identifiers, and the `ipam` filter against **both** backends on a loopback socket: the same six cases for NetBox, then phpIPAM repeating the happy path and the refusal (whose detail names phpIPAM, not NetBox) plus its `404`-is-a-denial case. That the two runs share every assertion is the trait earning its keep.
- `security.rs` — regression suite: deactivated accounts, wildcards, expiry, `CA:TRUE` CSRs, §6.7.1 `subproblems` on a multi-identifier rejection.
- `challenges.rs` — the challenge subsystem through the real router: pass/fail, terminal `invalid`, `Link: rel="up"`, wildcards.
- `config_driven.rs` — the only crate using a non-default `Config` (custom `base_url`, short nonce TTL, order/leaf validity).
- `revoke_cert.rs` — `POST /revokeCert` via `kid` or the certificate's own keypair, double-revoke, cross-account, CRL reflection.
- `audit.rs` — traceability through the real router, every request carrying a `ConnectInfo`: `newAccount` stamping `created_ip` once and `last_seen_*` moving on every accepted request (throttled inside `ACCOUNT_TOUCH_INTERVAL`, **never** when the address changed, **not at all** for a replayed nonce), `newOrder` freezing its own address, one `certificate_issued` row per issuance carrying account/profile/address/identifiers, the refusals (`badCSR`, `unauthorized`, `alreadyRevoked`, an unknown certificate) each recorded with the serial they targeted, a revocation with no reason leaving the column *absent* rather than `0`, an unparsable payload writing **nothing**, and the ACME account/order objects exposing none of it.
- `notify.rs` — the six firing sites through the real router, each with a `ConnectInfo` so `client_ip` has something to carry: every handler dispatches its event with the right subject, a repeat `newAccount` (a find, not a create) does **not** re-fire, and a backend that always fails still leaves the HTTP response untouched. Every assertion goes through a real job runner, since `dispatch` only queues — which is also the point of `a_dispatch_that_never_ran_is_still_owed_afterwards`: nothing is delivered when `dispatch` returns, the row is still there, and a runner started afterwards (as a restart would be) delivers it.
- `crl.rs` — `GET /crl` serves an empty, validly-parsing CRL before any revocation.
- `metrics.rs` — the counters moved by **real traffic through the real router**, which is what the inline suites cannot show: an ACME request reaching the middleware at all, and an issuance reaching `Auditor::record`. Deliberately never scrapes over HTTP — `/metrics` is on its own listener, which `src/cli/mod.rs`'s three-port test drives end to end (including the route being a `404` on the ACME socket) — so this reads the registry directly. `test_app_with_metrics` forces `metrics.enabled`, since `build_app` mounts the counting middleware only when it is on and a caller of that helper has by definition asked.
- `ca_chain.rs` — `GET /ca.pem`, the trust anchor beside it: served as `application/x-pem-file` and parsing as a certificate that is actually a **CA** (a leaf here would be silently useless), `404` for a backend with no anchor, and the one that makes the route worth having — the served bytes are the **tail of a genuinely issued chain**, so fetching the anchor and reading it off a certificate cannot install different bytes. Whether it stays unadvertised is pinned in `basic_endpoints.rs`, beside `/crl`.
- `http01_responder.rs` — `GET /.well-known/acme-challenge/{token}`, the `relay` backend's upstream-facing responder, through the real `build_app`. Pins the *mounting* (the relay's own publishing is covered in `src/signer/relay/mod.rs`): served verbatim with no trailing newline, an unknown token as a plain 404 rather than an ACME problem document, the route **absent entirely** when no backend has a store, and — the "routing splits by concern" invariant from the side where the client is a CA that knows nothing about ACME — no `Replay-Nonce`, no `Link: rel="index"`, unreachable by a profile's filter chain, but still inside the three hardening layers.
- `custom_signer.rs` — the `custom` signer backend through the real router: a genuine `openssl`-backed script issues and the finalize handler parses its chain end-to-end, plus a revoke round trip against the same script-backed order.
- `eab.rs` / `key_change.rs` / `renewal_info.rs` — each RFC surface's happy path plus its rejections. `renewal_info.rs` additionally pins the certID's AKI half being checked, `explanationURL` passthrough, revocation beating an upstream window, and the no-AKI back-compat fallback.
- `profiles.rs` — the multi-endpoint regression suite (cross-profile isolation, per-profile filters/CAs).
- `admin_cli.rs` — `src/admin/` operations against a real in-memory database.
- `admin_pages.rs` — the `/ui` HTML through the real `build_admin_app`, split from `admin_api.rs` because every assertion there parses JSON. Sign-in by form (cookie identical to the API's, a failure re-rendering with its *real* status), the auth redirect in both spellings over every page route, `mutating_page_endpoints()`, the **stored-XSS regression** (an EAB label, a path-supplied id, and a reverse name — the third is not operator text but *remote* text, since whoever controls the PTR for a client's address writes it), page-vs-fragment on one URL, every resource's reads and mutations, the layers (CSP, assets, the HTML fallback, `GET /`), and the order card's issued chain — the PEM rendered rather than the unreachable ACME URL, the `chain.pem` download asserted byte-for-byte against the stored chain with its `Content-Disposition`, and a `404` for both an unissued order and an unknown one (so the route never distinguishes the two to somebody guessing ids). The MFA half: the challenge page rendering for a `pending_mfa` session and **carrying no htmx** (the `login.html` twin — finishing a sign-in must work with JavaScript off), the form second step rotating the cookie, a half-authenticated cookie reaching *no* page in `authenticated_pages()`, `require_mfa` turning the challenge into an enrolment page that resumes rather than re-mints on reload, and the account page's whole lifecycle with its refusals as banners. `/ui/audit` is the read-only twin: the list, the fragment, one row in full, and the stored-XSS regression on a `User-Agent`.
- `admin_api.rs` — the JSON API through the real `build_admin_app`: sign-in (cookie attributes one by one, the three failures indistinguishable, rate limiting, session fixation), the session lifecycle (expired/idle/deleted/disabled), **the table-driven CSRF suite over every mutating endpoint** (missing, wrong, another session's token) plus the origin gate, every resource endpoint incl. pagination and `limit` clamping, all four revoke outcomes plus `profile_not_mounted` and a genuinely-issued order revoked once then conflicting, the EAB secret shown once and never again, contact validation matching `newAccount`'s, unknown paths answering the JSON 404 shape rather than an ACME problem document, the six response headers, and `/api/audit`'s read-only surface — it lists, filters, pages and resolves one row by id, and every mutating verb on it is unroutable, which is why it contributes nothing to `mutating_endpoints()`. The MFA section opens with **`a_factorless_login_is_completely_unchanged`** — the guard on the ~40 cases that go through `admin_login` — then covers the half-authenticated session opening nothing, promotion onto a brand-new token, replay, a refusal byte-identical to a wrong password, the limiter's second call site (and the password step *not* clearing it), `last_login_at` stamped at promotion, recovery codes, `require_mfa`'s forced enrolment, and `mfa_step_endpoints()` — the sibling table for the two routes that run the origin gate but not the CSRF check, kept out of `mutating_endpoints()` because with an active session they answer `401`/`303` rather than `403`.
- `jobs.rs` — the runner against a real database, for the claims one hand-driven loop cannot make: **two runners over one database never run one job twice** (25 jobs, two runners with separate counters, so "each ran ten" and "one ran twenty" are distinguishable), a row left `running` by a dead process reclaimed and finished by whoever starts next — with the dead process's attempt still counted — a notification dispatched by one component and delivered by the runner off the *same* row (the inline suites cover each half; only this shows they are one row), and a sweep going straight back to `ready` with a future `run_at` rather than settling.
- `reload.rs` — configuration reload against a real server on a real socket, and its own binary because each test points `ACME_PROXY_CONFIG` at a `config.toml` it just wrote (process state, so nextest's process-per-test isolation is what makes it safe). The live swap changing what the running port answers with the generation counting up; **a frozen key refused with the old configuration still serving** — the assertion the whole atomic-refusal decision exists for, and the one that must never be dropped; an unbuildable `[filter]` leaving the old generation up; a renewed certificate reaching the next TLS connection on the same port; and the admin listener rebuilding while its **login lockout survives**, the regression test for `LoginLimiter::rebuilt`.
- `logging_convention.rs` — the **only test that reads the crate's own source rather than running it**, and the enforcement half of the nine logging rules in `../CLAUDE.md`'s Conventions & gotchas. It walks `src/` from `CARGO_MANIFEST_DIR`, extracts every `info!`/`warn!`/`error!`/`debug!`/`trace!` invocation by balanced-paren scan, and asserts: a bare-literal `event` (`src/pemfile.rs` exempt), a known subsystem prefix, `db_` on everything under `src/sqlite/`, an `outcome` from the closed set agreeing with both the name suffix and the level, one name at one level (`request_completed` exempt), no `_length`/`_size` field suffix and no `as_millis()`, and — the one check reaching outside `src/` — that every event `doc/src/operations/monitoring.md` names is still emitted, so a rename that misses the operator catalogue fails CI. `the_scanner_finds_the_call_sites_it_is_supposed_to` is the guard on the guard: a scanner matching nothing would make every other assertion vacuously true.

## The e2e lab

`tests/e2e/` runs real ACME clients (certbot, acme.sh, lego) against a real `acme-proxy`, in containers started by `testcontainers-rs` — not shell scripts driving `podman-compose` (an earlier, fully removed version; see `tests/e2e/README.md`). `tests/e2e.rs` pulls every `tests/e2e/*.rs` file in as a module of one `e2e` test binary; every test is `#[ignore]`d, so `cargo nextest run`/`cargo test` skip them by default. Run with `cargo nextest run -E 'binary(e2e)' --run-ignored all` or `cargo test --test e2e -- --ignored` — nextest's plain positional filter matches test *names*, not binary ids, and no test name here contains "e2e", so a bare `cargo nextest run e2e` silently matches nothing (`0 tests run`, not an error). Docker or Podman is the only prerequisite (rootless Podman is auto-detected: `ensure_images_built` in `tests/e2e/common.rs` points `DOCKER_HOST` at the user's podman socket if unset — it checks `podman.socket` is already active and fails with a message naming `systemctl --user start podman.socket` rather than starting it itself); **not run by CI**.

`tests/e2e/common.rs`'s `Lab` is the harness every scenario builds on: it builds the seven images each scenario needs (`bind-e2e`, `acme-proxy-e2e`, `netbox-mock-e2e`, `phpipam-mock-e2e`, `certbot-e2e`, `acmesh-e2e`, `lego-e2e`, from the `Containerfile`s in this tree) once per run — guarded by an in-process `Once` plus a cross-process `flock`, since nextest runs each test as its own OS process — starts a dedicated podman network plus DNS/certbot/acme.sh/lego containers per `Lab::new`, and exposes `exec_in`/`exec_in_with_output` and `get_proxy_logs`/`get_proxy_upstream_logs`/`get_netbox_mock_logs`/`get_phpipam_mock_logs` (grep a container's log for a marker proving something real happened, e.g. `challenge_dns_01_matched`, `certificate_revoked`). `Lab::new_with_files` copies files into the `acme-proxy` container *before* it starts (testcontainers' `with_copy_to`), for scenarios like the `custom` signer where `signer.custom.script_path` must exist at startup.

**Three of the containers are conditional, and the condition is derived, not declared.** `netbox-mock` and `phpipam-mock` start only when some value in the scenario's `env` contains the `NETBOX_IP`/`PHPIPAM_IP` placeholder, and the upstream `acme-proxy` only under `new_with_upstream` — so a lab is five containers, not eight, for the twenty-nine scenarios that want no inventory. The placeholder *is* how a scenario asks for a mock's address, so deriving the need from it is what keeps there from being a second list to forget to update; `start_if_wanted` returns the same `Option` the `Lab` field already held, which is what lets all three go up in one `tokio::join!` rather than as sequential start/inspect round trips. Only the proxy waits, because only the proxy's environment names the others.

**A client's own idea of politeness can dominate the suite, and `certbot renew` is the worked example.** Its renew path applies `random.uniform(1, 60 * 8)` — a one-to-eight-minute sleep — whenever `sys.stdin.isatty()` is false, which it always is under `podman exec`. It exists to spread real clients' load across Let's Encrypt and is pure dead time against a CA in a container on the same host. Unnoticed, that one line averaged four minutes, made the suite's wall clock a coin flip run to run, and was larger than every other cost here combined; `certbot.rs` passes **`--no-random-sleep-on-renew`**, and any new `certbot renew` call site must too. The general lesson is worth more than the flag: when a scenario is slow, check what the *client* decided to do before assuming it is the server or the harness — nothing in this repository's own code was responsible.

**Build cost is a design constraint here, not an afterthought** — the lab is on a developer's inner loop, and it had drifted to seven minutes a run (34 tests, now ~50 s). Three things keep it down and each is load-bearing: the root `.dockerignore` is an **allowlist** (`Cargo.toml`, `Cargo.lock`, `src/`, `migrations/`), so editing prose no longer invalidates `COPY . .`; `tests/e2e/.dockerignore` drops `*/target` from a context that was 128 MB and shipped on six of the seven builds; and the root `Containerfile` builds `--profile e2e` over `RUN --mount=type=cache` (which replaced cargo-chef — chef cached the dependency half and nothing cached the crate itself, which was the expensive half). Adding a file the build genuinely needs means adding a `!` line to that allowlist; the failure is a loud missing-file error, not a subtle one.

Covers: real challenge validation per type (`http_01.rs`/`dns_01.rs`/`tls_alpn_01.rs`, `challenge.bypass = false`, the last via lego — neither certbot nor acme.sh implement a tls-alpn-01 responder); account key rollover (`key_change.rs`, also lego, via `accounts keyrollover` — added in lego v5.0.0, so `tests/e2e/lego.Containerfile` builds a pinned v5.3.1 from source rather than Alpine's 4.x package; neither certbot's vendored `acme` library nor current acme.sh implement rollover at all, the latter having dropped `--update-account-key` with no replacement); EAB (`eab.rs`); every filter incl. the `ipam` one against two Rust mocks (`filters.rs`: `test_netbox`, `test_netbox_fhrp_group_membership` — acme.sh's interface is in FHRP group 41 and certbot's is in none, so only acme.sh gets the group's service name — `test_phpipam`, and `test_phpipam_unknown_address`, which is its **own TLS-enabled lab** because lego is the only container the phpIPAM mock holds no row for and lego refuses a plain-HTTP ACME server: any lego scenario needs `server.tls.enabled` plus `--tls-skip-verify`, and `lego run` takes its flags *after* the subcommand); multi-profile isolation (`profiles.rs`); the `relay` signer backend against a second instance of the same image (`relay_signer.rs` — all three `challenge_strategy` values; the `http01` scenario points the *upstream's* `challenge.http_01.port` at 3000, since the downstream binds one socket and the lab has no reverse proxy to stand in for the port-80 forwarder a real deployment needs); the `custom` signer backend (`custom_signer.rs`); renewal info (`ari.rs`); the admin CLI against a real running server (`admin_cli.rs`); **renewal** through both clients (`certbot renew --force-renewal` in `certbot.rs`, `acme.sh --renew --force` in `acme_sh.rs`) — a second full order under an existing account, which is the operation a deployment performs far more often than a first issuance and which nothing exercised; revocation through acme.sh as well as certbot (§7.6 has two authorization forms, and two clients is how a client-specific assumption would surface); and **`SIGHUP`** (`reload.rs`), the one path `tests/reload.rs` cannot reach because it calls `ReloadHandle::reload()` directly. That scenario writes a `config.toml` into `/data` — the image's `WORKDIR`, where `Config::load` looks — and signals PID 1 **twice**, because the second signal is the trap: a one-shot handler would leave it at its default disposition, which is *terminate*. One bug this lab caught that the unit suite couldn't: hickory surfaces both NXDOMAIN and an empty NOERROR answer as `Err`, not `Ok` with zero records — fixed by checking `NetError::is_no_records_found()` in `src/dns.rs` before treating a lookup failure as an error.
