# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An **ACME (RFC 8555) server** in Rust/[axum](https://docs.rs/axum), serving certificate clients (certbot, acme.sh) over the full account → order → authorization → challenge → finalize → certificate flow, plus revocation.

**At 0.1.0, the first release. Before 1.0.0 the database schema is the *only* compatibility guarantee** — `migrations/` is frozen and append-only (see Database & migrations below before touching the schema), so an upgrade is starting the new binary against the existing database. Nothing else is frozen: config keys, profile names, the ACME URLs derived from them, the admin JSON API, log event names and the CLI may all be renamed or removed. That is the point — it is what lets a design be improved rather than accumulate a compatibility layer for every shape it has ever had. Three obligations come with it, and they are the whole cost:

1. **The change is listed in `CHANGELOG.md` under the release's `### Breaking` heading**, naming the old spelling and the new one. `CHANGELOG.md`'s `## Compatibility` section is the canonical statement of this policy; the copies in `README.md`, `SECURITY.md` and the book are one sentence each and link there.
2. **A removed or renamed config key is refused by name at startup** wherever practical, so an unmigrated configuration stops the server instead of coming up looking configured. This is a one-line error message and a diagnostic, not a compatibility path — several exist already (`signer.backend = "acme_proxy"` → `relay`, `filter.check.<name>.type = "netbox"` → `ipam`, `filter.enabled`/`filter.exempt_paths`/`filter.custom_enabled`), and they all go away at 1.0.0. Note a key must still *parse* to be refused by name, which is why `src/config/types/filter.rs` keeps the removed fields and `LIST_KEYS` keeps their entries.
3. **Never an alias, a dual syntax or a legacy lowering.** Delete the old shape; do not teach the new code to keep reading it.

- **Accounts** — `newAccount` (find-or-create by pubkey, `201`/`200` + `Location`), `POST /acct/{id}` (contact update / deactivate, `kid`-authenticated per §6.2).
- **Orders** — `newOrder` normalizes and validates each identifier, then creates one `Authorization` per identifier (each with one `Challenge` per enabled type) in a single transaction. Authorizations/challenges are read via signed POST-as-GET; a challenge is triggered with `POST /chall/{id}` (`{}` payload). An authorization is **deactivated** (§7.5.2) by POSTing `{"status": "deactivated"}` to the same URL its POST-as-GET reads.
- **Challenge validation** — pluggable subsystem (`src/challenge/`): `http-01`, `dns-01`, `tls-alpn-01`, selected by `challenge.enabled`. Validation is **on by default**; `challenge.bypass = true` turns it off, marking a triggered challenge `valid` with no network check. (It defaulted to `true` until the zero-config posture was reconsidered: an empty `filter.rules` plus a default bind on every interface made that an open CA.) Validation is inline/synchronous, under `challenge.timeout_ms`. Both success and failure return `200` + the challenge object (§7.5.1), never an HTTP error. **`ChallengeRegistry::default()` still bypasses** — it is a test convenience, deliberately diverging from `from_config(&ChallengeConfig::default())`, since the suite has no `http-01` responder on port 80.
- **Wildcards** (`*.example.com`) — accepted only when `dns-01` is enabled; the authorization sits on the base name, flagged `"wildcard": true`, offering `dns-01` alone.
- **Finalize/certificate** — `finalize` parses the CSR and issues via a pluggable **signer backend** (a persistent local CA is the one implemented); certificate retrieval is signed POST-as-GET (§6.3).
- **Revocation** (`POST /revokeCert`, §7.6) — authorized by either the order's account `kid` **or** the certificate's own key pair (embedded `jwk`, no account — the RFC's accountless case). Calls the signer's own `revoke` (so the local CA's CRL, RFC 5280, served unauthenticated at `GET /crl`, actually reflects it) before recording on the order; a repeat is `alreadyRevoked`. Orthogonal to the order state machine (a revoked order's `status` stays `valid`) and not gated on account status.
- **Access control** — a **policy engine** (`src/filter/`, off by default): named `[filter.check.<name>]` entries with a `type`, and `[filter.rule.<name>]` entries whose `when` is a boolean expression over check names, selected and ordered by `filter.rules`. First match wins. Seven types: `allowed_ip`, `path`, `reverse_dns`, `identifiers`, `eab`, `ipam` (asks the configured inventory whether the client's own address owns the names — see IPAM below) and `custom` (an operator script). With `challenge.bypass` on, this is the only access control there is. **This replaced the flat all-must-pass chain wholesale**: `filter.enabled`, `filter.exempt_paths`, `filter.custom_enabled` and the four per-type sections are gone, each refused by name at startup, and there is deliberately no legacy path — the standing pre-1.0 rule above, so the redesign deleted rather than accumulated. A check answers three ways (`Pass`/`Fail`/`Undecided`) and conditions combine by **Kleene logic**, which is the whole point: `mgmt-net or inventory` survives an inventory outage while `inventory` alone is still a retryable 500.
- **IPAM** (`src/ipam/`, `[ipam]`, off by default) — one question, asked of whichever inventory an estate already keeps: *which names does this address own?* Two backends, `netbox` and `phpipam`, behind an `Ipam` trait; `filter::ipam` is the only consumer and is the sole place a denial is decided. That split is enforced by the types: `IpamError` has no "denied" variant, so every failure to reach the inventory is a retryable 500 and an outage can never fail open — only `AddressNames::Unknown` ("no record of this address") is inventory-sourced denial. Each backend takes a **`sources`** list naming where a permitted name may come from (`dns_name`/`custom_field`/`device`/`vip`/`fhrp`); empty or unknown is a startup error, and a source belonging to the *other* backend is refused by name. `device` stays a fallback (read only when the address said nothing); `vip` and `fhrp` are unions. **`fhrp` is a membership proof and the direction of the query is why**: client address → its interface → `fhrp-group-assignments?interface_id=…` → group ids → their addresses. Nothing is ever looked up by group name, by the service address, or by the requested identifier, so no query can reach a group the client is not recorded in. The budget lives on `IpamRegistry` (one `timeout_ms` covering all four-or-five requests) the way `ChallengeRegistry`'s does, so a backend added later cannot forget it. **This was `filter.netbox` until 0.1.x**; the filter name, the section and three keys all moved, and the old spelling is a *named* startup error — a diagnostic so an unmigrated config stops the server rather than coming up looking configured, the `signer.backend = "acme_proxy"` → `relay` treatment, not a compatibility path.
- **Traceability and the audit trail** (`src/audit/`, `[audit]`) — the CA records who asked it to sign or withdraw a certificate, and from where. `accounts` carries `created_ip`/`created_ptr` plus `last_seen_at`/`last_seen_ip`/`last_seen_ptr` (surfaced by `render_account_json`/`render_account_detail_text`, so the `/ui` account card, `GET /api/accounts/{id}` and `account show` all name both addresses; the **listing** shows the last-seen one where it used to show a public-key fingerprint, which identifies nothing an operator scanning a list is looking for), `orders` carries `created_ip`/`created_ptr`, and `audit_log` takes one row per CA action *and per refusal* (`certificate_issued`/`certificate_issue_failed`/`certificate_revoked`/`certificate_revoke_failed`) with the profile, the actor, the address, its reverse name, the identifiers, the User-Agent and the `x-request-id`. **Nothing ever compares against these** — pinning an identity to an address breaks CGNAT and mobile, the same reasoning as `admin_sessions.created_ip` — and none of them reaches an ACME object: the wire format is RFC 8555's and stays that way, so this is admin-CLI/web-visible only. The reverse lookup is best-effort under `audit.reverse_dns_timeout_ms` and every failure is a `NULL`, never a refused request. Read with `acme-proxy audit list|show`, `GET /api/audit`, `/ui/audit`; pruned with `audit cleanup --older-than` or `audit.retention_days`, and **by nothing else** — the web admin's audit surface is deliberately read-only, since a stolen session that could erase the trail would make the trail prove nothing.
- **Background work** (`src/jobs/`, `[jobs]`) — a durable queue: one `jobs` row per unit of work the server owes itself, and one runner per process draining it. Replaced a bare `tokio::spawn` inside the `relay` signer backend whose state lived on its `upstream_orders` row and whose `SignerBackend::resume` sweep re-created it at startup — that bought *recovery* but never *retry*, since with nowhere to record that an attempt had failed there was nothing to schedule a second one, so a five-second upstream blip terminally invalidated a client's order. A handler answers `Done`/`Retry`/`Failed`/`Reschedule`; **the `Retry`/`Failed` split is the whole design** (a network, a proxy or a 503 has decided nothing, so ask again; a CA that stated a reason has, so believe it), and `abandon` fires **exactly once** when a job is retired for good and never between retries — which is what keeps an order `processing` through a blip instead of `invalid`. Claiming is a guarded `UPDATE … RETURNING` (the `admin_sessions.mfa_attempts` shape) taking a **lease**, so a crashed process's work is reclaimed by expiry rather than only by a restart, and two runners over one database cannot both take a row. `attempts` increments at *claim*, so a job that kills the process still exhausts its budget. Retrying is bounded twice: by `jobs.max_attempts` (frozen onto the row at enqueue) and by the row's own `deadline`, which the relay sets to the local order's `expires` — past that the order is refused on read, so a certificate obtained upstream could never be collected. `enqueue` wakes the runner through a `Notify` rather than leaving it to `jobs.poll_interval_ms`, because the ACME client that triggered the work is already polling its order. `Reschedule` is periodic work without a cron table: one row that re-queues itself, whose identity the partial unique index keeps unique — `jobs::retention`'s own sweep is the worked example, and the reason there is no fourth `spawn_*_reaper`. The three existing reapers (nonce, audit, admin session) deliberately stay in-memory interval loops: they sweep tables with no durability requirement, and moving them would add a database row to schedule a database delete.

- **External Account Binding** (§7.3.4, `src/eab.rs`, off by default) — `newAccount` requires a credential minted out of band by `acme-proxy eab create`; credentials live in the database (revocable without a restart), and `onlyReturnExisting` lookups are exempt since they never create an account.
- **Key rollover** (§7.3.5, `src/key_change.rs`, `POST /keyChange`) — swaps an account's key given a nested inner JWS proving possession of both; refuses with `409` + `Location` when the new key already belongs to another account.
- **Renewal Information** (RFC 9773) — two surfaces. `GET /renewalInfo/{certID}` is the unauthenticated "when should I renew this?": from the upstream CA's own opinion (`explanationURL` included) when the signer backend has one, otherwise a local estimate (last third of validity), and a window entirely in the past once revoked — checked *before* the backend, so a locally revoked certificate is never talked out of renewing. `newOrder`'s **`replaces`** (§5) names the predecessor certificate, is checked against §5's three correspondence rules, stored, and reflected back on every read; a second order naming the same predecessor is `409 alreadyReplaced`.
- **TLS termination** (`src/tls.rs`, off by default) — `server.tls.enabled` serves HTTPS on `bind_address` instead of cleartext, from supplied PEM or a self-signed cert generated on first run (the alternative to a reverse proxy, since §6.1 expects ACME over HTTPS). `tls::acceptor_from` is the shared load-or-generate + rustls builder; `from_config` is the ACME wrapper (keeping the `tls_disabled`/`tls_base_url_mismatch` warnings) and `admin_from_config` the web admin's.
- **Web admin** (`src/webadmin/`, `[admin]`, off by default) — a **second listener** on its own socket, serving no ACME: HTML pages at `/ui` and a JSON API at `/api`, both thin layers over the same `src/admin/` operations the CLI uses, behind password authentication and an opaque session cookie. The pages are minijinja + a vendored htmx (no npm, no CDN, no build step); each list/detail route serves a whole document or the bare fragment htmx swaps, chosen off `HX-Request` so there is still one bookmarkable URL per resource. Deliberately carries **no admission control** (the availability concern is credential brute force, which the login limiter handles) and **no filter chain** (a per-profile ACME concern). Access control is the bind address, TLS and the session. `GET /` redirects to `/ui/`, and the router's **fallback is HTML** — `/api`'s JSON fallback is scoped inside its own nest, so a script still gets the admin error shape on the paths a script uses. A strict `Content-Security-Policy` (`default-src 'none'`, no `unsafe-inline`/`unsafe-eval`) joins the five existing header layers. Startup **refuses** a non-loopback `admin.bind_address` while `admin.tls.enabled` is false — the cookie is always `Secure`, which browsers silently decline over plain HTTP off `localhost`, so the symptom would be "login succeeds then immediately logs out" with nothing in any log. Sign-in is **two steps once a second factor exists** (`src/admin/totp.rs`, RFC 6238): the password mints a short-lived `pending_mfa` session (`PENDING_MFA_TTL`, 5 min, a constant not a config key) that reaches only the routes finishing the login, and proving a code **rotates** it into a fresh `active` one — a new token and a new CSRF token, never an `UPDATE state`, since the pending token crossed the wire before authentication completed. `record_success`/`mark_logged_in`/`log_login(true)` all moved to that promotion: leaving `record_success` at the password step would let somebody holding a correct password clear their own limiter bucket on every attempt and brute-force six digits. There are **two** promotion paths and they share `finish_mfa`/`finish_enrolment` for exactly that reason — the second is the `require_mfa` bootstrap, where setting a factor up *is* the second step, and before it was extracted the two front ends had already drifted (the API side doing none of the three, the pages side one). Guessing is bounded **twice**: `LoginLimiter` by peer address, and `admin_sessions.mfa_attempts` by session — the latter because a `pending_mfa` cookie is valid from any address on purpose (`created_ip` is forensics, never compared), so the address-keyed bound alone gives an attacker `login_max_attempts` fresh guesses per source, of which one IPv6 /64 supplies 2^64. It is a single `UPDATE … RETURNING`, which is also what makes it race-free on a listener that deliberately has no admission control, and past the cap the pending row is **deleted** rather than merely refused. **Changing a live factor takes the password again** (`check_step_up`, on `begin_totp`/`disable_totp`/recovery-code reissue, and only when a factor already exists): each of those also revokes every *other* session and supersedes the recovery codes, so without it one stolen cookie converts into a lockout only `admin user totp reset` on the host undoes. A first enrolment is ungated — it protects nothing, and a password there would stand in front of the `require_mfa` bootstrap.

Invalid input is rejected with RFC 8555 `application/problem+json` documents (`src/error.rs`). Orders/authorizations are refused once `expires` has passed, and a `deactivated` account cannot request issuance at all.

## Commands

```bash
cargo build                 # build
RUST_LOG=info cargo run     # run the server on [::]:3000 (IPv6 any) by default. Set RUST_LOG for logs.
cargo run -- serve          # same as above, spelled out — `serve` is the default subcommand
cargo nextest run           # runs the Rust unit + integration tests (see Testing — nextest, not `cargo test`)
cargo fmt                   # format
cargo clippy                # lint
cargo llvm-cov nextest --summary-only   # test coverage (needs `cargo install cargo-llvm-cov cargo-nextest` + `rustup component add llvm-tools-preview`)
```

The same binary also carries admin subcommands, so a full deployment never needs a separate tool:

- `filter show [--profile <p>]|explain [--profile <p>] [--client-ip <ip>] [--identifier <name>]… [--path <p>] [--account-id <id>] [--json]` — read and test an endpoint's access policy. Both **build** it exactly as startup does, so every startup refusal reaches an operator here too, which makes `show` the cheapest pre-restart check. `explain` reports all three stages (connection/newOrder/CSR) because every one must allow, and lists checks short-circuited past — a skipped check and a passing one are indistinguishable in the outcome otherwise. **It really runs the policy**, scripts and inventory lookups included, and names what reached outside the process; that is also why there is no web-admin twin, since the address and names are caller-chosen and it would be script-exec plus SSRF from one stolen cookie.
- `account list|show <id> [--json]|update-contact <id> --contact <uri>|deactivate <id>|delete <id>`
- `order list [--account-id <id>] [--status <s>]|show <id>|delete <id>|revoke <id> [--reason <n>]`
- `audit list [--profile <p>] [--account-id <id>] [--order-id <id>] [--cert-serial <hex>] [--event <e>] [--outcome success|failure] [--since-days <n>] [--limit <n>] [--offset <n>] [--json]|show <id> [--json]|cleanup --older-than <days>` — the CA's audit trail. `list` is **paged** (default 50) unlike `account list`/`order list`, because this table grows a row per issuance for the life of the deployment, and it always prints `N of M row(s)` so a page is never mistaken for the whole trail. An unknown `--event`/`--outcome` is refused **by name**: passing it through to SQL would answer "no rows", which looks exactly like "nothing happened". `cleanup` is the only command in the binary that destroys audit history, so it is confirm-gated and its prompt names the count.
- `nonce cleanup [--ttl-seconds <n>]`
- `upstream show [--json] [--profile <name>]|register [--eab-kid <kid>] [--eab-hmac-key-file <path>] [--profile <name>]` — `--profile` is optional only when the configuration defines exactly one; `signer` is a per-profile section, so acting on the global base would be acting on nothing
- `eab create [--label <text>] [--json]|list [--json]|show <kid> [--json]|revoke <kid>`
- `admin user create <username> [--password-file <path>]|list [--json]|passwd <username> [--password-file <path>]|delete <username>|disable <username>|enable <username>`
- `admin user totp status <username> [--json]|reset <username>|recovery-codes <username>` — the operator side of the second factor. **No `enrol`**, and the omission is the `--password` argument verbatim: there is no way to enrol from a terminal that does not put the base32 secret in scrollback and shell history. `reset` is the lockout lever (confirm-gated: it removes a control) and takes the codes and every session with it. — the web admin's operators; this is how the panel is bootstrapped, since it has no sign-up page
- `admin session list [--username <u>] [--json]|revoke --user <u>|--all`

**The password never goes in argv**: there is no `--password` flag and a test asserts clap rejects one, the same rule (and reasoning — `ps`, shell history) as `upstream register`'s EAB secret. It arrives on stdin or via `--password-file`; no `rpassword`, whose echo suppression needs a real TTY and would break the injectable-`BufRead` seam the whole `src/admin/` layer is testable through. `admin user passwd` and `admin user disable` both revoke every session that user holds — a password changed because it may have leaked, leaving the leaked session alive, would be a change in name only.

`eab create` prints the generated HMAC secret only once — stored but never shown again, so a lost one is replaced, not recovered. `delete`/`cleanup` prompt for confirmation (naming what cascades) unless `--yes`/`-y`. `order revoke` — the operator-side equivalent of `POST /revokeCert`, for an out-of-band report a client can't or won't act on — is **not** confirm-gated, since revocation only ever tightens trust; it calls the signer's `revoke` directly.

### CI

`.github/workflows/ci.yml` has six jobs. **test**: `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings`, `cargo llvm-cov nextest --fail-under-lines 96` (`main.rs` excluded — it's pure socket/exit wiring; `nextest` rather than plain `cargo test` is load-bearing, see Testing), `cargo test --doc` (llvm-cov skips doc-tests, so this is the only thing that compiles the startup example in `src/lib.rs`), and `cargo doc -D warnings` — which `cargo test --doc` does *not* cover, since it compiles the examples and not the intra-doc links, of which this crate has a great many. `rustdoc::private_intra_doc_links` is allowed deliberately: the library exists so the tests and `main.rs` can reach it, not as a published API, and a public item explaining itself by naming the private thing it delegates to is the good outcome. **msrv**: `rust-version` read out of `Cargo.toml` (a floor stated in two places drifts) plus `cargo check --locked --all-targets --all-features`; until this existed the manifest's own comment admitted CI did not verify it. **hsm**: the `hsm` feature is off by default and `--all-targets` does not enable features, so `cargo clippy --all-targets --features hsm -- -D warnings` and `cargo nextest run --features hsm` get their own job (with `softhsm2` installed) — deliberately *not* folded into `test`, whose `--fail-under-lines 96` a feature-gated file sits outside of entirely. **supply-chain**: `cargo deny check` against `deny.toml`, with `all-features = true` — at `false` an optional dependency is simply absent from the graph, so `cryptoki` would never be checked for advisories at all. **docs**: `mdbook build doc/` plus `python3 doc/lint.py`, on every change rather than only ones touching `doc/` — `mdbook.yml` deploys the book but runs *only* on a push to `main`, so until this job existed nothing built the book on a pull request, and `create-missing = false` makes a `SUMMARY.md` entry with no file a build **failure** rather than a stub. `doc/lint.py` is the style gate: 80-column prose (tables, fences, headings, `### Reference` entry lines and link-only lines exempt), no numbered headings, no trailing whitespace, every fence tagged, every relative link and `#anchor` resolving, and **no configuration key documented in two files** — that last one is the rule that actually rots, since two copies of a default drift silently. Both workflows install `mdbook`/`mdbook-mermaid` pinned through `taiki-e/install-action`, and every action in `mdbook.yml` is now SHA-pinned like `ci.yml`'s. **e2e** (nightly only): the three challenge scenarios against real ACME clients in containers; it builds six images and starts four containers per scenario, so it is minutes rather than seconds. Keep clippy warning-clean and formatted, or CI fails.

**Coverage gotcha**: a handler carrying `#[instrument]` reports far lower coverage than it actually has. The attribute moves the body into a generated `async` block, so signature lines show 0 hits and body lines carry no region at all (`handlers/authz.rs` sits around 40% while `tests/challenges.rs` drives nearly every branch in it). Check `cargo llvm-cov report --text` for the file before writing tests against the percentage. (A `tracing` subscriber in tests does **not** fix this — measured, it moves the total by 0.03 points; `tests/common/mod.rs` installs one anyway so the `Display`/`Debug` impls behind every log field actually execute.)

### Database & migrations

Migrations are embedded via `sqlx::migrate!()` and run **automatically at startup**. `sqlx migrate add <name>` creates a timestamped file in `migrations/`. Query calls use runtime `sqlx::query(...)`, not the compile-time `query!` macros, so `DATABASE_URL` is **not** required to compile.

The SQLite file is `sqlite.db` by default (gitignored, auto-created). `Database::connect(url)` / `connect_in_memory()` (tests) live in `src/sqlite/db.rs`. `connect` pins two pragmas: `foreign_keys(true)` (the schema's `ON DELETE CASCADE` depends on it) and `journal_mode = WAL` (every response writes a nonce row, and the default rollback journal takes a database-wide exclusive lock per write).

Migrations are **append-only as of 0.1.0** — every file in `migrations/` is frozen and a schema change means `sqlx migrate add <name>`, never an edit to a committed file. (`20260815120000_add_jobs.sql` is the first written under this rule rather than merely covered by it, and is what the shape looks like in practice: a new table in a new file, adding nothing to any existing one.) This is the one surface the freeze covers, and the only compatibility guarantee before 1.0.0 (see What this is above: config keys and everything else may still be renamed). It reverses the rule that held until the release: while the server had never been deployed, a schema change was made by editing the migration in place and running `rm -f sqlite.db*`. That is no longer available, because a database out there has already run these files and `sqlx` tracks each one by a **checksum** — editing a committed migration makes every existing deployment fail at startup with a checksum mismatch, not silently diverge. Two consequences worth internalising:

- **A new column is a new file**, even when it obviously "belongs" to an existing table. `ALTER TABLE ADD COLUMN` is cheap in SQLite; adding it to the table's original `CREATE TABLE` is the thing that breaks.
- **A `CHECK`/`UNIQUE`/FK change needs a table rebuild in a new migration** (SQLite cannot add one to an existing table), which is why several constraints below were declared before anything wrote them — `admin_users.totp_*` and `admin_sessions.state`'s `'pending_mfa'` are the worked example.
- **The freeze covers the comments too**, which is why three migrations still call the relaying signer backend `acme_proxy` (`20260727120000`, `20260730120000`, `20260809120000`) after it was renamed to `relay` everywhere else. A stale comment is not worth a checksum mismatch on every existing deployment. Grep results in `migrations/` are read-only, full stop.

Current schema facts worth knowing:

- `accounts.profile` / `orders.profile` (`NOT NULL`); `accounts` keyed `UNIQUE(profile, pubkey)`; `eab_keys.profile` is nullable (`NULL` = valid at every endpoint) — this is the profile isolation boundary (see Profiles below). Request-path lookups take the profile; the admin CLI uses the deliberately unscoped `find_any_by_id`/`find_any_by_kid`.
- **Every FK is indexed** (SQLite indexes only PK/UNIQUE, so these were full table scans on every order read and challenge trigger) and **`ON DELETE CASCADE`** (so an account/order can actually be deleted).
- **`CHECK (status IN (…))`** on the four status columns — transitions are raw string literals spread across three modules, so this catches a typo before it parks a row in an unreachable state.
- **`UNIQUE(order_id, identifier)`** on `authorizations`, **`UNIQUE(authz_id, type)`** on `challenges`.
- The revocation columns (`cert_serial`, `cert_pubkey`, `revoked_at`, `revocation_reason`) are plain nullable `ALTER TABLE ADD COLUMN`s, no rebuild — none carries a `CHECK`/`UNIQUE`/FK. `cert_serial` is indexed (`POST /revokeCert` looks an order up by it on every request), as is `orders.replaces` (RFC 9773 §5's "already replaced?" runs on every `newOrder` carrying one). `accounts.terms_of_service_agreed` is nullable on purpose: `NULL` means "no terms were advertised when this account was created", which is not `false`, and renders as an absent member.
- **`audit_log` (`20260809120000`) is the one table with no foreign keys**, and that is the point rather than an omission: an audit row must survive `account delete` and `order delete`, and a `CASCADE` would delete the evidence along with its subject. `account_id`/`order_id` are plain columns naming a row that may be gone, `identifiers` is frozen into the row for the same reason, and `id` is an autoincrementing integer (an operator types it, and `AUTOINCREMENT` stops SQLite reusing the rowid of a purged row). `outcome` is denormalized from `event` and written from the single definition in `AuditEvent::outcome`, so "show me everything refused" is an index lookup rather than `event LIKE '%_failed'` written out in three front ends. `CHECK`s on `event`, `outcome` and `actor_kind`; indexes on `created_at` (the listing *and* the retention sweep), `account_id` and `cert_serial`. Rows are only ever INSERTed — there is no setter and no `UPDATE` anywhere in the crate.
- The traceability columns on `accounts`/`orders` sit in those tables' **own** migrations *and* in `20260727120000_indexes_and_constraints.sql`, which rebuilds both — under the old edit-in-place rule an addition to only the first was silently discarded by the rebuild's `INSERT … SELECT`. That hazard is now **historical**: it explains the shape of the committed files, and cannot recur, since a new column arrives in a new migration that runs after every rebuild rather than being retrofitted into one that precedes it. `upstream_orders` likewise gained `client_ip`/`client_ptr`/`user_agent`/`request_id`, which is where the finalize request's context is parked so the `relay` relay can name it when it settles minutes later.
- The `authorizations` `CHECK` already permitted `'deactivated'` before §7.5.2 was implemented, so that needed no migration — only `Authorization::mark_deactivated`.
- `admin_users`/`admin_sessions` (`20260808120000`) are the web admin's own identities and never join to an ACME concept. Deliberately **the opposite of `eab_keys`**: that migration justifies a *retrievable* secret because HMAC verification needs the same secret back every request, whereas a password is only compared, so it is one-way and unreadable (a lost one is replaced, never recovered). A session stores only `hex(SHA-256(token))` — not the password KDF, since a 256-bit CSPRNG token has no dictionary to slow down and the hash exists solely so a database read yields nothing replayable. `admin_users.totp_*` and `admin_sessions.state`'s `'pending_mfa'` were declared before anything wrote them, because a `CHECK` is exactly what SQLite cannot add later without a table rebuild; both are live now. The two TOTP secrets are **plaintext BLOBs on purpose** — verification recomputes the HMAC, so the server needs the same bytes back every attempt: that is `eab_keys.hmac_key`'s situation, not a password's, and any wrapping key would live in the same directory as the database. `state` is **write-once at INSERT** (there is no setter; `AdminSession::promote` inserts a new row and deletes the old one). `admin_recovery_codes` is the third table: single-use codes hashed the *password* way, because a recovery code is only ever compared — a table rather than a JSON column so consumption is `UPDATE … WHERE id = ? AND used_at IS NULL` with `rows_affected` deciding a race, the `nonces` primitive; `used_at` is stamped, not deleted, so "7 of 10 remaining" is a count and a spent code leaves a trail. `created_ip`/`user_agent` are forensics only, never compared against the live request (address pinning breaks CGNAT/mobile, UA pinning breaks on the next browser update). The same migration adds `idx_orders_created_at`/`idx_orders_status_created_at`, which the admin's newest-first cross-account listing needs and the ACME path never did.

## Configuration

`Config::load()` (`src/config/`) layers, lowest precedence first: **built-in defaults → optional `config.toml`** (gitignored; `config.toml.example` documents every key) **→ `ACME_PROXY_*` environment variables**. Point at a different file with `ACME_PROXY_CONFIG=/path/to/config`.

### Profiles: the server serves ACME only through them

An **ACME endpoint is a profile** (`[profiles.<name>]`), mounted at the reserved `/profile/<name>` namespace — `[profiles.le]` answers at `{base_url}/profile/le/directory`. Several profiles can run in one process, over one listener and one database, each with its own signer, filters, challenge validators and EAB requirement. **At least one enabled profile is required**; `Config::resolve_profiles` fails with a copy-pasteable minimal config otherwise.

Load-bearing rules, all pinned by tests:

- **The path is derived from the name, never configured** (`Profile::new` + `PROFILE_PREFIX` in `src/lib.rs`); names match `^[a-z0-9-]+$`. This makes a collision with a root route impossible and needs no path-validation rule — but the name is public API, since it's in every `kid` and order URL a client stores.
- **Routing splits by concern.** The root router serves `GET /health`, `/` → redirect, the server-wide layers, and — only when some profile's signer backend has an `http-01` token store to publish — `GET /.well-known/acme-challenge/{token}` (see `signer.relay.challenge_strategy = "http01"`; the route is not mounted at all otherwise). Each profile router serves the ACME resources — including `/crl` — plus its filter chain, the `Replay-Nonce` middleware, the `Link: rel="index"` middleware, and the 405/404 fallbacks that make those answers `application/problem+json` instead of empty bodies. So `/health` is never filtered, mints no nonce, and carries no index link — which is why nothing needs exempting for a health probe. A `path` check matches the profile-stripped path. **Tracing is the one thing that does not split this way**: the `request` span and the access line are server-wide (`middlewares::access`, outermost of everything), because a request id that stops at the profile boundary is no use on the routes that sit outside it — `/health`, the http-01 responder, and every admission-control refusal. Each profile router contributes only the `profile` field, recorded onto that span by its outermost layer.
- **Inheritance is per key, not per section.** Global `[signer]`/`[filter]`/`[challenge]`/`[eab]`/`[order]` are the base every profile overlays; `Config::merged_sections` merges the *raw* `config::Value` trees, so a profile setting only `challenge.bypass` keeps the **global** `challenge.enabled` rather than reverting it to the compiled default. Arrays replace wholesale, never append. Precedence: profile key > global key > compiled default.
- **Profiles are a database boundary, not just a URL prefix.** `accounts`/`orders` carry a `profile` column, `accounts` keyed `UNIQUE(profile, pubkey)` — one client key at two endpoints is two independent accounts (`tests/profiles.rs` is the regression suite).
- **`enabled`** (default `true`) parks a profile without deleting its config, and doubles as the one key an environment-only profile needs (`ACME_PROXY_PROFILES__LE__ENABLED=true`).
- **Signer backends are shared by configuration, not built per profile** (`signer::build_backends`): two profiles with identical `[signer]` share one `Arc<dyn SignerBackend>`, since two `LocalCa` instances over the same files would each rewrite the CRL from their own in-memory ledger. Two profiles sharing `ca.key` while differing elsewhere is a startup error.

Gotcha: a list-valued key **inside** a profile needs its runtime key registered for list parsing — `Config::load` scans the environment for `ACME_PROXY_PROFILES__<NAME>__…` before building its sources, or e.g. `ACME_PROXY_PROFILES__LE__CHALLENGE__ENABLED` is silently dropped (the same trap the global `LIST_KEYS` registry below exists for).

### Keys

(env override in parentheses; `__` separates nested keys, `_` separates the prefix)

- `database.url` — SQLite URL. Default `sqlite://sqlite.db` (`ACME_PROXY_DATABASE__URL`).
- `server.bind_address` — listen socket. Default `[::]:3000` (`ACME_PROXY_SERVER__BIND_ADDRESS`).
- `server.base_url` — public base URL for the directory + JWS `url` checks, no trailing slash. Default `http://localhost:3000` (`ACME_PROXY_SERVER__BASE_URL`).
- `server.max_concurrent_requests` / `server.admission_wait_ms` / `server.request_timeout_ms` / `server.max_body_bytes` — admission control for the ACME routes (`src/middlewares/admission.rs`). Defaults `100` / `50` / `60000` / `131072`. Past the limit a request waits `admission_wait_ms` then gets `503` + `Retry-After` — it is **shed, not queued**, which is what `GlobalConcurrencyLimitLayer` used to do. `GET /health` is mounted **outside** all of it. `request_timeout_ms` **must exceed** `challenge.timeout_ms` and (when that backend is installed) `signer.custom.timeout_ms`, since both run inline in a request; `Profile::build_all` refuses to start otherwise.
- `server.tls.enabled` — serve HTTPS on `bind_address` **instead of** cleartext (one listener, not two). Default **`false`**. `base_url` is **not** rewritten — set it to `https://…` yourself or every signed request fails the §6.4 URL check (`ACME_PROXY_SERVER__TLS__ENABLED`).
- `server.tls.{cert_path,key_path}` — PEM chain (leaf first) + key. Defaults `server.pem`/`server.key`; a self-signed certificate is generated and written when either is missing.
- `server.tls.handshake_timeout_ms` — budget for one TLS handshake. Default `10000`; handshakes run concurrently, so this never delays another client.
- `admin.enabled` — the web admin listener. Default **`false`**. Process-wide, so **not** in `PROFILE_SECTIONS`.
- `admin.bind_address` / `admin.base_url` — defaults `127.0.0.1:3001` / `http://localhost:3001`. `webadmin::check_config` (run from `serve_on` before anything binds) refuses: a bind equal to `server.bind_address`, a `base_url` that does not parse or has no host, and **a non-loopback bind while `admin.tls.enabled` is false** (a hard error, not a warning — see the "What this is" bullet). A scheme mismatch is a `admin_base_url_mismatch` warning, the `tls_base_url_mismatch` treatment. `base_url` is load-bearing **four** ways (CSRF origin check, generated cert host, the host in the `otpauth://` label an authenticator shows, and later a WebAuthn RP id), so the resolved origin is logged as `admin_origin_resolved` at startup.
- `admin.session_ttl_seconds` / `admin.session_idle_timeout_seconds` — `43200` / `3600`. Absolute (never extended) and idle (advanced on use, at most once per `SESSION_TOUCH_INTERVAL` = 60 s, so a polling page is not a stream of WAL writes). Whichever expires first wins. Sessions outlive a restart, so `spawn_session_reaper` runs for the process's life, not just at startup.
- `admin.login_max_attempts` / `admin.login_window_seconds` — `5` / `300`. Checked **before** the password hash: 600 000 PBKDF2 iterations is a DoS lever otherwise. Keyed on the peer address; **no forwarded-header handling on this listener**, since trusting `X-Forwarded-For` without an allowlist would let any caller spoof the key. Also the cap on `admin_sessions.mfa_attempts`, which is the same number bounding a thing the address key cannot — see the web-admin bullet above.
- `admin.require_mfa` — default **`false`**. Governs only the operator who has *no* factor: with it on, their next sign-in lands on the enrolment page and the session stays `pending_mfa` until they finish. An operator who *has* one is challenged either way. Deliberately **not** "refuse a password-only login" — enrolling needs a session and a session would then need a factor, so that would brick the panel including the way in to fix it. Does not retroactively end sessions that predate it; `acme-proxy admin session revoke --all` is the lever that does. While it is on and somebody has no factor, startup warns `admin_mfa_enrolment_pending` on **every** start, the `challenge_validation_bypassed` treatment.
- `admin.max_body_bytes` / `admin.page_size_max` — `65536` / `200`. `?limit=` is clamped, not refused (default page size 50).
- `admin.template_dir` — per-file overrides of the `/ui` templates, mirroring `notify.template_dir` (same loader shape: disk name first, embedded default second). Default `""`. `check_config` refuses a path that is not a directory **and compiles every template at startup**, so a broken override stops the process instead of serving a `500` later.
- `admin.tls.{enabled,cert_path,key_path,handshake_timeout_ms}` — `false`/`admin.pem`/`admin.key`/`10000`. Same one-listener-not-two shape as `[server.tls]`; separate paths on purpose, since the two listeners answer to different names. Log lines gain a `listener = "acme"|"admin"` field while keeping the same event *names*.
- `nonce.ttl_seconds` — nonce freshness window. Default `300`.
- `audit.reverse_dns` / `audit.reverse_dns_timeout_ms` / `audit.retention_days` — `true` / `2000` / `0`. Process-wide, so **not** in `PROFILE_SECTIONS`: the trail describes the CA, not one of its endpoints. There is deliberately **no `audit.enabled`** — recording who asked the CA to sign something is what a CA does, and the only thing an operator can switch off is the reverse lookup, which costs a network round trip and has estates where it can never succeed. `retention_days = 0` keeps everything for ever (the right default for a trail whose value is that it is complete); non-zero spawns a daily sweep beside the nonce reaper, running the identical `DELETE` as `audit cleanup --older-than` via the shared `admin::ops::audit_cutoff`.
- `jobs.{poll_interval_ms,max_concurrent,max_attempts,retry_base_seconds,retry_max_seconds,lease_seconds,retention_days}` — `1000` / `8` / `5` / `30` / `3600` / `300` / `7`. Process-wide, so **not** in `PROFILE_SECTIONS`: one queue, one table, one runner, and a per-endpoint retry budget would make a job's pacing depend on which profile happened to queue it. No list-valued key, so no `LIST_KEYS` entry and no count assertion to bump. There is deliberately **no `jobs.enabled`** — the queue is how the server finishes work it already promised a client, so switching it off would strand orders rather than disable a feature. `poll_interval_ms` bounds only *scheduled* work (an enqueue wakes the runner directly). `max_concurrent` was `MAX_CONCURRENT_RELAYS`, a constant inside the relay backend, and carries the same value and the same reasoning. **`max_attempts` is frozen onto each row at enqueue** where every other key is read afresh per attempt, so raising it applies to new work and not to a waiting backlog. `retry_max_seconds` is a real ceiling: the jitter only ever subtracts, since a key documented as "where the doubling stops" must not be overshot by the jitter after it. `retention_days` is **non-zero by default**, unlike `audit.retention_days` — a finished job is a receipt, not evidence — and `0` stops the sweep being scheduled at all.
- `logging.filter` — `EnvFilter` fallback used only when `RUST_LOG` is unset. Default `acme_proxy=info`. (No `tower_http` directive: the `TraceLayer` it silenced is gone — the access line is this crate's own `request_completed` event, see `src/middlewares/access.rs`.)
- `logging.json_format` / `logging.flatten_event` — JSON output, and whether a record's own fields sit at the top level or nest under `fields`. Defaults `false`/`false`.
- `logging.target` — `stdout` or `stderr`. Default `stdout`, and load-bearing: `tests/e2e/common.rs` gates container readiness on `server_startup` appearing on **stdout**, so flipping the default fails e2e as a start *timeout* rather than an assertion.
- `logging.ansi` — ANSI colour in the human-readable format. Default `true`; ignored under `json_format`.
- `logging.span_events` — `none`/`close`/`full` → `FmtSpan`. Default `none`; `close` gives per-span busy/idle timing.
- All six are validated in `cli::init_logging` before anything is installed (`parse_target`/`parse_span_events`/`build_env_filter`, each returning `Result<_, String>`); an unknown value exits with a message rather than falling back. `run()` is still the only place that prints and exits.
- `order.validity_seconds` — the ACME **order object's** `expires` window (housekeeping, not the cert's validity). Default `604800` (7 days).
- `signer.backend` — issuance backend selector. Default `local_ca`; the other values are `relay` and `custom`.
- `signer.custom.{script_path,timeout_ms,args}` — the `custom` backend (`src/signer/custom.rs`): delegates `issue`/`revoke` (and, if `supports_crl`/`supports_renewal_info` are set, `crl`/`renewal_info` too) to an external script, on the same env-var/stdin-JSON/exit-code contract as the `custom` filter check but prefixed `ACME_SIGNER_*` and always JSON-on-stdin (CSR/certificate DER travel only there, standard base64, never through an env var or ACME's own base64url). An empty `script_path` is a startup error. Exit code `3` on the `issue` hook means `BadCsr`; any other non-zero exit is an internal failure. This backend always answers synchronously — no `processing` state, since a shelled-out script can't call back later.
- `signer.local_ca.{cert_path,key_path}` — CA cert/key PEM paths. Defaults `ca.pem`/`ca.key`.
- `signer.local_ca.key_type` — CA key algorithm. Default `ecdsa-p256`.
- `signer.local_ca.leaf_validity_days` — issued leaf validity (distinct from `order.validity_seconds`). Default `90`.
- `signer.local_ca.crl_path` — where the CRL (RFC 5280) is written and served from `GET /crl`. Default `ca.crl`, regenerated on every revocation and startup. The durable ledger is a JSON sidecar next to it (extension swapped to `.json`), not the CRL's own DER round-tripped back.
- `signer.local_ca.crl_distribution_points` / `signer.local_ca.ca_issuer_urls` — where a *relying party* fetches that CRL and this CA's own certificate, written into every issued leaf as `cRLDistributionPoints` (RFC 5280 §4.2.1.13) and `authorityInfoAccess`/`caIssuers` (§4.2.2.1). Both `[]` by default, and an empty list emits **no extension at all** rather than an empty SEQUENCE, so a leaf stays byte-identical to what this CA issued before the keys existed. **Deliberately not derived from `server.base_url`**: the value is frozen into every certificate signed while it is set, so a rename would break certificates already issued, and `{base_url}/profile/<name>/crl` is served *inside* the profile router — behind that profile's filter policy, i.e. refused to exactly the relying parties the extension exists for (the `path.rs` trap). Several `crl_distribution_points` entries are one `DistributionPoint` holding several URIs — one CRL, several mirrors — never several DistributionPoints, which would claim several different CRLs. Validated and DER-encoded **once at startup** (`local_ca/policy.rs`'s `LeafPolicy`, built in `load_or_generate` before either branch touches disk), so a bad URL is a startup error rather than a 500 at finalize and `issue` does no ASN.1 work per request; credentials in the URL, a non-`http(s)` scheme and any value `Url` would normalize (a missing trailing `/`, an environment list's un-trimmed `a, b`) are each refused naming the key and the value. `http://` is unwarned on purpose — fetching a *signed* CRL over TLS is the validation loop this extension breaks. rcgen has no AIA support, so that half is a `CustomExtension` whose DER is built with `simple_asn1`; `id-ad-ocsp` is never written, since there is no responder. Two profiles sharing one CA share the list too (`LocalCaConfig`'s `Debug` is the signer dedup key, and `signer_paths` already refuses differing configs over one `ca.key`).
- `signer.local_ca.key_source` — where the issuing private key lives: `file` (default, everything above) or `pkcs11`. Anything else is a startup error; so is `pkcs11` on a binary built without `--features hsm` (never a silent fallback to the file key, which would leave the CA key on disk while the operator believed it was in hardware).
- `signer.local_ca.pkcs11.{module_path,token_label,slot_id,key_label,key_id,pin,pin_file}` — the token (`src/signer/local_ca/pkcs11.rs`, `#[cfg(feature = "hsm")]`). `module_path`/`key_label` required; `token_label` preferred over `slot_id` (slot numbers move across re-plugs); `key_id` disambiguates two keys sharing a label, which is otherwise a startup error rather than a coin flip. `pin_file` (trailing whitespace trimmed) wins over `pin`, and neither set is a startup error. **`pkcs11` never generates a CA** — `cert_path` must already exist and `key_path` is untouched — and the token key's SPKI is cross-checked against `cert_path` at startup, which is *stricter* than the file path, where nothing verifies the pair.
- `signer.relay.*` — the **relaying** backend: this server keeps serving ACME to its own clients, who keep proving domain control to *it*, but the certificate comes from a real upstream ACME server this becomes a client of. `directory_url` (required), `account_key_path` (default `upstream_account.key`, ECDSA P-256, `0600`; the upstream's assigned account URL is stored beside it as `.kid`, so only the *first* startup contacts the upstream), `contact` (list), `challenge_strategy` (`bypass`/`dns01`/`http01`), `poll_interval_ms` (`2000`), `poll_timeout_secs` (`300`). With `dns01`: `dns01.provider` (only `rfc2136`) and `dns01.rfc2136.{server,zone,tsig_key_name,tsig_key_secret,tsig_algorithm}` (`tsig_key_secret` is **standard** base64, unlike the EAB secret's base64url, and legitimately long-lived so it stays in config). With `http01`: **nothing** — there is no `[signer.relay.http01]` table, because the responder is a route on this server's own root router (`/.well-known/acme-challenge/{token}`, off an in-memory token store) rather than a second listener or a webroot. What it needs instead is out of the process's reach: a reverse proxy forwarding or redirecting that path here from port 80 of every name being issued, which `from_config` states as a `signer_relay_http_01_selected` info on every startup. It cannot prove a wildcard (nothing answers on the name `*.example.com`) and refuses one by name, pointing at `dns01`. An upstream EAB credential authorizes exactly one `newAccount` call and is useless afterwards — registration itself only ever runs once, guarded by the `.kid` sidecar next to `account_key_path`. It can be supplied two ways: `acme-proxy upstream register --eab-kid <kid>`, reading the secret on **stdin** or via `--eab-hmac-key-file` (never a flag — argv is visible in `ps`), used once and dropped; or `[signer.relay.eab]` (`kid`/`hmac_key`, both base64 — url-safe, unpadded url-safe, or standard), read by `serve` itself on the first startup with no `.kid` sidecar yet. The config path trades away the CLI path's whole reason for existing — no bootstrap secret sitting in configuration for the life of the server — for not needing a separate imperative step; `serve` logs a `signer_relay_eab_secret_in_config` warning on **every** startup for as long as `hmac_key` stays non-empty after registration succeeds, the same "stays visible for as long as it lasts" treatment as `challenge_validation_bypassed`/`ipam_netbox_tls_verification_disabled`. Either field of `[signer.relay.eab]` set without the other, or a `hmac_key` that isn't valid base64, is a startup error. If the upstream demands EAB and neither mechanism supplies one, `serve` fails at startup naming both.
- `meta.terms_of_service` / `meta.website` / `meta.caa_identities` — the optional `meta` members of the directory (§7.1.1). All empty by default and omitted when empty. `terms_of_service` is the one with teeth: setting it turns on §7.3.3, so `newAccount` then refuses a request without `termsOfServiceAgreed: true` (`403 userActionRequired` + `Link: rel="terms-of-service"`), and the account object starts reflecting `termsOfServiceAgreed`. `caa_identities` is advertised only — this server does no CAA checking.
- `challenge.enabled` — types each new authorization offers, in order (`http-01`/`dns-01`/`tls-alpn-01`). Default `["http-01"]`. **Empty, or an unknown name, is a startup error** — even when bypassing.
- `challenge.bypass` — skip validation entirely; a triggered challenge is marked `valid` with no check. Default **`false`**. With it on, `[filter]` is the only access control — which is why it is no longer the default.
- `challenge.timeout_ms` — budget for one validation attempt. Default `5000`; validation runs *inside* `POST /chall/{id}`, so this is also that request's worst case.
- `challenge.http_01.{port,https_port,follow_redirects,max_redirects,max_response_bytes}` — defaults `80`/`443`/`true`/`5`/`4096`.
- `challenge.tls_alpn_01.port` — default `443`.
- `dns.resolver` — `host:port` of the nameserver **every** DNS lookup this server makes goes through (the `dns-01` TXT query, the connect target `http-01`/`tls-alpn-01` resolve before reaching out, and the `reverse_dns` check's PTR/forward lookups). Default unset (system configuration).
- `proxy.{http_url,https_url,no_proxy}` — the forward proxy every outbound HTTP client dials through (`src/proxy.rs`, `[proxy]`, all three empty by default). Process-wide, so **not** in `PROFILE_SECTIONS`: egress is a property of the network position the process runs in, not of one endpoint. There is no `proxy.enabled` — the presence of a URL is the switch, matching `ipam.backend = ""`. An `https://` target is reached by a **`CONNECT` tunnel**, an `http://` one is *forwarded* (absolute-form request line + `Proxy-Authorization`), and `tls-alpn-01`'s raw TLS probe is tunnelled too. Each key falls back to its conventional environment variable when empty (`$http_proxy`; `$https_proxy` then `$HTTPS_PROXY`; `$no_proxy` then `$NO_PROXY`) — **uppercase `HTTP_PROXY` is deliberately not read** (httpoxy, CVE-2016-5385: under CGI a client-supplied `Proxy:` header lands in the environment under that name; this server is never CGI, but Go dropped it for the same reason and matching costs nothing). `no_proxy` entries are `*`, a domain, `.domain`, an address or a CIDR — a **network entry is only ever compared against a target that is already a literal**, since resolving a name to test one would be a lookup per request and a race with the connect that follows; an entry carrying a port is a startup error. **Loopback and `localhost` bypass unconditionally**, before `no_proxy`, so an inherited shell `http_proxy` cannot route this server's own loopback traffic through a corporate proxy — which is also why `OutboundProxies::always` exists (`#[cfg(test)]`): without it every transport test against a proxy on `127.0.0.1` would take the direct path and pass for the wrong reason. `https://`/`socks5://` proxy URLs are refused **by name**, and an unreachable proxy is an error every time — never a fallback to a direct connection, which would dial around a controlled egress path exactly when the control fails. **SMTP (`notify.email`) and the RFC 2136 updates (`signer/relay/dns01.rs`) are not HTTP and dial directly**, documented rather than silently absent.
- `filter.rules` — the `[filter.rule.<name>]` entries to evaluate, in order. Default `[]` (no filtering, with a `filter_disabled` warning). An array, so a profile overriding it replaces the sequence — order *is* the policy.
- `filter.default` — `allow`/`deny` when a rule was applicable at a stage and none matched. Default `deny`. **Never consulted at a stage no rule applies to**, or a policy of nothing but `identifiers` checks would refuse every connection before a name was mentioned.
- `filter.rule.<name>.{when,then,message,mode}` — the condition (see `src/filter/expr.rs`), `allow`/`deny`, the operator's own refusal text, and `enforce`/`warn`. A **map**, not `[[filter.rule]]`: tables merge per key under profile inheritance, so `[profiles.staging.filter.rule.x] mode = "warn"` dry-runs one rule and inherits the rest — an array of tables could not be partially overridden and would not round-trip through `ACME_PROXY_*` at all. Deliberately carries no list-valued field, so this table needs no runtime env scan.
- `filter.check.<name>.{type,stages,…}` — one check. Keys are **flattened** (`allow`, not `allowed_ip.allow`), so a key belonging to another type is a startup error naming both — `#[serde(tag = "type")]` would have given per-variant fields for free but serde's `deny_unknown_fields` does not apply to internally tagged variants, which would make the misplaced key silently ignored. `stages` overrides where an instance decides; naming a stage the type cannot serve is a startup error. **Only checks a selected rule names are built**, which is what lets a global section hold a library of them and each profile pick a subset. `type = "netbox"` is refused by name.
- `filter.check.<name>.{allow,deny}` — **globs** on the name-matching types (`*` is one label; on `path`, one path segment), CIDRs on `allowed_ip`. `{allow,deny}_regex` are the auto-anchored regexes and union with them; regex was the biggest footgun here and is no longer the only spelling.
- `filter.trusted_proxies` / `filter.forwarded_header` — CIDRs whose forwarded-for header is believed, and the header name. Defaults `[]` / `x-forwarded-for`.
- Per-type check keys: `allowed_ip`/`path` take only `allow`/`deny` (both empty is a startup error — the check would be inert); `reverse_dns` adds `require_forward_confirm`/`timeout_ms` (`true`/`2000`) and is connection-only by default though *capable* of both stages; `identifiers` adds `allowed_types`/`allow_wildcards` (`["dns","cn"]`/`false` — off by default since patterns are anchored, so a `deny` for `secret\.example\.com` doesn't match the literal `*.example.com` even though the certificate covers that name); `eab` adds `kids`/`require_active`; `custom` takes `script_path`/`timeout_ms`/`pass_stdin`/`args` (`""`/`5000`/`true`/`[]`). **An empty list always means the type's natural default, never "none"** — an unset list env var arrives as `[]`, so it has to.
- `ipam.backend` / `ipam.timeout_ms` — which inventory the `ipam` filter consults (`""` / `netbox` / `phpipam`; anything else is a startup error) and the budget for one **whole** lookup however many requests it takes. Defaults `""` / `5000`. Per-profile, so two endpoints may consult different inventories; `PROFILE_SECTIONS` therefore has **eight** entries, not seven.
- `ipam.netbox.{url,token,custom_field,sources,vip_roles,ca_cert_path,insecure_skip_verify}` — defaults `""`/`""`/`acme_allowed_names`/`["dns_name","custom_field","device"]`/`["vip","vrrp","hsrp","glbp","carp","anycast"]`/`""`/`false`. `url`/`token` required once selected; `token` is a secret and belongs in the env var. `custom_field` is only *required* when `sources` names `custom_field` or `device`, and `vip_roles` only when it names `vip` — a rule with nothing behind it would be noise. The role is re-checked on the answer as well as sent as a filter, so a wrong filter parameter can never degrade into "every address on the device". `insecure_skip_verify` logs a warning on **every** start while set, deliberately not once-only, so it stays visible for exactly as long as it's needed (e.g. to wait out an expired NetBox certificate).
- `ipam.phpipam.{url,app_id,token,custom_field,sources,ca_cert_path,insecure_skip_verify}` — defaults `""`/`acme`/`""`/`custom_acme_allowed_names`/`["dns_name","custom_field","device"]`/`""`/`false`. Auth is the static **app code** on a bare `token` header (phpIPAM's own scheme, not `Authorization`); the user/password session-token scheme is deliberately unimplemented. `app_id` must be one path segment — it is interpolated into every API path, so a stray slash would silently retarget the API rather than fail. `sources` supports only the first three: naming `vip`/`fhrp` here is refused **by name**, since phpIPAM records no roles and no redundancy groups. **A `404` from `addresses/search` is an answer, not a failure** — phpIPAM says "no such address" that way, which is the entire reason `ipam::http::JsonApiError` carries the status; every other non-2xx is still an outage.

Gotchas:

- `config`'s `Environment` reuses the nested `separator` as the prefix separator unless `prefix_separator("_")` is set explicitly — `src/config/mod.rs` pins it, otherwise every `ACME_PROXY_*` var is silently dropped.
- Array-valued keys additionally need `try_parsing(true)` + `list_separator(",")` + a `with_list_parse_key` entry, or the env var is silently dropped. `src/config/mod.rs` keeps these in the `LIST_KEYS` const — **add new array keys there**. A regex containing a literal comma (`{2,3}`) is therefore file-only.
- An array-valued env var **set to the empty string** (`${VAR:-}`-style shell defaults) is present, not absent — `config` can't tell the difference — and `"".split(',')` yields one empty-string element, not `[]`. Every `LIST_KEYS` field runs through `empty_string_is_no_values` to collapse that back to `[]`; a new list field needs the same `#[serde(deserialize_with = "empty_string_is_no_values")]` attribute or it becomes a startup error the moment something leaves it unset that way.

## Testing

`cargo nextest run` runs the suite. Tests use an in-memory SQLite (`Database::connect_in_memory()`) and an in-memory local CA (`LocalCa::generate_in_memory`) — no disk file or network is ever touched.

**nextest is required, not preferred.** The `custom` script tests in `signer`/`filter`/`notify` exec a file they just wrote; under plain `cargo test`, which runs tests as threads of one process, that intermittently fails `ETXTBSY` — another thread's `Command::spawn` forks while the file's write descriptor is still open, and the forked child holds it until its own exec. Nothing in the test can avoid this (the kernel checks the inode, so writing elsewhere and renaming into place does not help either), so `cargo test --lib` fails roughly one run in three. nextest's process-per-test isolation removes it entirely.

Anything calling `Config::load()` in a test must hold `config::ENV_LOCK` (crate-wide, `#[cfg(test)]`, in `src/config/mod.rs`) — `ACME_PROXY_*`/`ACME_PROXY_CONFIG` are process state, so a test setting one while another loads makes the second read the first's variables. It is one lock for the whole crate on purpose: per-module locks serialise a module against itself and nothing else.

**Harness** (`tests/common/mod.rs`): `test_app_full` is the single place the app is built — it mounts one profile named `default` through the real `build_app`, so paths carry the endpoint prefix (the harness exports `HOST`, `PROFILE`/`PREFIX`/`BASE`, and `p("/newOrder")`). Variants: `test_app_with_db` (exposes the `Arc<Database>` so a test can close its pool), `test_app_with_signer`/`_filter`/`_challenges` (inject a custom backend), `test_app_with_profiles` + `TestProfile` (multi-endpoint app). Because `oneshot` has no socket, `send_from`/`post_from`/`fetch_nonce_from` insert the `ConnectInfo<SocketAddr>` extension by hand, which is how a test gives filters a client address. For the web admin: `admin_config()`, `test_admin_app`/`test_admin_app_with_signer` (the latter for tests that must genuinely *issue* before revoking), `test_admin_app_logged_in` → `AdminSessionHandle { cookie, csrf }`, plus `admin_request`/`admin_login`/`session_cookie_token`/`json_body`. `test_admin_app` and `test_app_full` share `one_profile`, so the two cannot drift into mounting different endpoints. ## Architecture

Request flow for a signed ACME POST (e.g. `newAccount`):

1. **`add_nonce_middleware`** (`src/middlewares/nonce.rs`) wraps every route of a profile, but mints only where RFC 8555 asks for it (`mints_nonce`): **every response to a POST** (§6.5, errors included) and **`newNonce`** in all three of its forms (§6.3/§7.2). Not on `GET /directory`, `/crl`, `/renewalInfo/{id}` or the fallbacks — each of those used to cost a committed database write for a nonce nobody asked for, on exactly the traffic that dominates a real deployment. The layer stays **outside** the filter layer, so a POST a filter refuses still carries one.
2. **`AcmeRequest<T>` extractor** (`src/extractors/acme.rs`) is the core of the codebase. Its shared `verify_jws` core **checks `Content-Type: application/jose+json`** (§6.2 — a mismatch is `415`, before the body is even read, so a rewritten header never burns a nonce), parses the flattened JWS, base64url-decodes the protected header, **rejects any `crit`** (RFC 7515 §4.1.11: this server implements no critical extension, so every value is unrecognized), **verifies the signature with `ring`**, then **checks the JWS `url` against the route actually reached** (§6.4) and **consumes the nonce** (§6.5). Hoisting these checks here makes them structural: a new signed route can't forget them, and no handler repeats the old four-line preamble. The account's `last_seen_*` stamp is here for the same reason — this is the one place every `kid`-authenticated request funnels through — and **after** the nonce check, so a replayed request never moves the mark; the reverse lookup runs only once `Account::needs_touch` has said the write is worth doing. Three extractors build on it: `AcmeRequest<T>` (decode + deserialize the payload), `AcmePostAsGet` (require an empty payload, else `malformed`), and `AcmeOptionalPayload<T>` (`Option<T>`, `None` when empty) — the last exists for the authorization resource, where one URL serves both a POST-as-GET read and a §7.5.2 deactivation. Supports EC `ES256` and RSA `RS256`. Two mutually exclusive auth forms per §6.2 (both `jwk`+`kid` or neither → `malformed`): an embedded **`jwk`** is verified and re-encoded as DER SPKI by hand (`simple_asn1`); a **`kid`** is resolved to its account and verified against the account's **stored** DER-SPKI, after checking the SPKI's own `AlgorithmIdentifier` OID matches the client's `alg` — so the verification algorithm never rests on `alg` alone. EC coordinates must be exactly 32 octets (RFC 7518 §6.2.1.2), or a short/long one parses as a *different* point, registering one key as two accounts. `SignatureError` (`Malformed`/`BadAlgorithm`/`BadSignature`/`Encoding`) maps to `malformed`(400)/`badSignatureAlgorithm`(400, carrying the `algorithms` list §6.2 requires)/`unauthorized`(401)/`server_internal`(500); an unknown `kid` → `accountDoesNotExist`.
3. **Handler** (`src/handlers/account.rs`) does its own work — `url`/nonce were already checked. `post_new_account` honours `onlyReturnExisting` (§7.3.1: look up, never create), else find-or-creates by `pubkey`, and returns `201`/`200` + `Location`. `post_account` requires `account.pubkey == pubkey` (ties `kid` to the target it modifies), rejects a `deactivated` account, then applies the update.
4. **Order handlers** (`order.rs`, `authz.rs`) pin ownership through shared helpers: `signer_account` resolves the signer's account and **refuses a `deactivated` account** — since every order-side operation funnels through it, one check covers all seven endpoints. `load_owned_order` requires `order.account_id == account.id` (unknown → `malformed`, wrong owner → `unauthorized`) and refuses an expired order unless already `valid`; expiry is checked *after* ownership so it can't be used to probe order IDs. `post_new_order` normalizes each identifier, validates shape (`well_formed_name`: a `*` is legal only as a single leading `*.`, **and what is left has to be a DNS name** — bounded length, non-empty labels from `[A-Za-z0-9_-]`, no leading or trailing hyphen. `_` stays legal, since underscore labels are ordinary on the internal networks this server exists for. The syntax half is load-bearing rather than tidy: `filter::custom` comma-joins the identifiers into `ACME_FILTER_IDENTIFIERS`, and `challenge::http_01` hands the value to `Url::parse`, which reads `internal.corp/` as the host `internal.corp` — a name the anchored `deny` regex `internal\.corp` does not match. With `challenge.bypass` on, where `[filter]` is the only access control there is, that was a deny-list bypass.) then policy (`types_for` empty → `rejectedIdentifier` naming `dns-01`) — collecting **every** offending name rather than the first, so a multi-name order comes back as one `compound` problem with a `subproblems` entry per identifier (§6.7.1; a lone rejection stays its own type, unwrapped) — checks `replaces` if present (RFC 9773 §5), then writes the order plus one `Authorization`/`Challenge` set in **one transaction** — a half-written order would be finalizable for names never authorized. `post_authz` serves both §7.5's read and §7.5.2's deactivation off one URL, told apart by whether a payload arrived; deactivating demotes a `ready` order back to `pending` and is refused once the order is `valid` (revocation, not deactivation, is what undoes issuance). `post_challenge` refuses an expired *or deactivated* authorization, short-circuits three already-decided states (a `valid` challenge, a terminal `invalid` one, and a `pending` sibling on an already-`valid` authorization), otherwise computes the key authorization and calls `challenges.validate`. Both outcomes are then recorded in **one transaction** (`commit_validation`/`commit_validation_failure`): challenge, authorization and order together, with the in-memory sync deferred until after the commit. Success promotes the order to `ready` once every **authorization** (not challenge) is `valid`, and that readiness read happens *inside* the transaction — from the pool, two concurrent validations of one order could each read before the other's write landed and neither would promote. Three separate statements also left a gap where an order sat `pending` with every authorization `valid`, which nothing re-derives. §7.5.2's deactivate-and-demote pair is one transaction for the same reason. **Both outcomes return `200` with the challenge object** (§7.5.1 — a 4xx would surface as a transport failure to certbot's `acme` library) plus a `Link: rel="up"` header that library requires. `post_finalize` requires `status == "ready"` (else `order_not_ready`); on issuance, `BadCsr` leaves the order `ready`/retryable, `Internal` also marks it `invalid` (terminal, pollable). **Everything past the `ready` check is audited**: the success as `certificate_issued`, and each of the five refusals below it (bad base64, unparsable CSR, CSR/order mismatch, a filter denial, the backend's own `BadCsr`/`Internal`) as `certificate_issue_failed` with the problem type as `reason`. Above that line the refusals are protocol bookkeeping with no CA action attempted, and recording them would bury the ones that matter. The `IssueOutcome::Processing` arm writes **no** row — nothing has been signed yet — and instead parks the request's `ClientContext` on the `upstream_orders` row, so the single row written by `signer::relay::relay::settle` minutes later can still name the client that asked.

Every one of `post_revoke_cert`'s refusals is likewise an audit row, including the unknown-certificate case — a stream of those is somebody enumerating serials, which is exactly what the trail is for. The two payloads that never reach an identifiable subject (unparsable base64, unparsable DER) write nothing, because a row naming nothing is noise.

**Certificate revocation** (`post_revoke_cert`, §7.6): the JWS need not name an account (either the order's `kid` or the cert's own `jwk`), so it resolves authorization itself rather than through `signer_account`. It decodes the certificate, looks the order up by serial (`find_by_cert_serial`, indexed) and confirms an **exact DER match** against the stored leaf — the safety net a serial-only lookup can't provide on its own. **Never compare a key re-derived from the submitted DER**: the DER match above already proves it equals the stored one, so re-deriving would let anyone who merely observed the certificate on the wire revoke it with an unrelated key. It checks the verified `pubkey` against the order's account or its stored `cert_pubkey`, refuses `alreadyRevoked` (checked *after* authorization, so an unauthorized caller can't probe revocation state) and an out-of-range reason code, then calls the signer's `revoke` **before** `Order::revoke` — the CA-side action is authoritative, so a signer failure leaves the order un-revoked for a retry. `get_crl` serves the signer's CRL as `application/pkix-crl`; routed but deliberately not advertised in the directory (CA infrastructure, not an ACME resource).

**Models** (`src/sqlite/`):

- `nonce.rs` — single-use (`DELETE` + `rows_affected == 1`), within `nonce.ttl_seconds`. `cleanup()` runs at startup **and then on an interval for the process's life** — every response mints a nonce, including `GET /newNonce`, so a startup-only sweep would leak.
- `account.rs` — `find_or_create` dedupes by pubkey (§7.3). There is deliberately **no** unauthenticated `GET /acct/{id}` — it would leak `contact` to anyone holding the id, which `newAccount` already publishes in `Location`. `post_account` accepts either `kid` or `jwk`, since the pubkey check authorizes either.
- `order.rs` — `find_by_account` is unfiltered (the admin CLI counts it to say what a delete cascades); `find_active_by_account` is the §7.1.2.1 view the orders-list URL serves; `search` is the **only** implementation of the profile/account/status filter, in SQL — the CLI used to hold a second one in Rust over `list_all`, which meant one meaning of `--status` written twice and a whole table loaded to filter three fields. `mark_pending` is the state machine's one backwards transition, and exists only so §7.5.2 can hold for an order that already reached `ready`. `revoke()` stamps `revoked_at`/`revocation_reason` **without touching `status`** (RFC 8555 defines no "revoked" order status). `to_json` never exposes the revocation columns; that state is admin-CLI-visible only (`src/admin/render.rs`). The `processing` status is set when a signer backend defers issuance (`relay`); `local_ca` never reaches it, since it answers inline.
- `authz.rs` — each `Challenge` gets its own random token (§8), since every key authorization derives from it. `mark_invalid` deliberately doesn't stamp `validated` (§8 defines it as the time of a *successful* validation).

**Wildcard storage convention**: a wildcard authorization's row keeps the wildcard form (`*.example.com`); `to_json` renders the base name plus a separate `"wildcard": true`. Storing the base name instead would break the canonical order `["example.com", "*.example.com"]`: `UNIQUE(order_id, identifier)` compares serialized JSON, both rows would be identical, and the whole order would fail to persist — fixing that would need a `wildcard` column *inside* the constraint, i.e. a full table rebuild. Deriving the base name costs a `strip_prefix` and no migration.

**Signer abstraction** (`src/signer/`): the `SignerBackend` trait — `issue`/`revoke` (async, so a network-delegating backend can await IO; `revoke` must be idempotent), `crl_der` and `renewal_info` (both default to "nothing to say here", the sensible answer for a backend with no opinion), plus two more defaulted methods a single backend overrides: `jobs` (the durable-queue handlers this backend needs — see `src/jobs/`; it replaced a `resume` hook that re-spawned tasks at startup, so recovery is one case of a queue rather than a mechanism of its own) and `http01_tokens` (hand `build_app` the store the `/.well-known/acme-challenge/{token}` route serves from — a getter on the trait rather than a `build_app` parameter, for the same reason `crl_der` is one). `issue` also takes a `RequestedValidity` — the order's own `notBefore`/`notAfter` (§7.4). A backend may ignore it (both delegating ones do, since the upstream/script decides), but `LocalCa` honours it *clamped*: the request may only narrow its `leaf_validity_days` window, never widen it, and an inverted request is discarded whole. `renewal_info` returns a `RenewalWindow { start, end, explanation_url }` rather than a bare pair, so RFC 9773 §4.2's `explanationURL` survives the relay. A third backend, `custom.rs`'s `CustomScriptSigner`, delegates all four hooks to an external script — the signer-side counterpart to `filter::custom`'s `CustomScriptFilter`, with the same process-hardening (`env_clear()`, minimal `PATH`, `kill_on_drop(true)`, `tokio::time::timeout`). The default backend, `local_ca.rs`'s `LocalCa` (via `rcgen` 0.14), generates a self-signed CA (`pathLenConstraint: 0`) if none exists; the key is created with `OpenOptions::mode(0o600).create_new(true)`, not chmod'ed after the fact, avoiding a window where any local user could read it. `issue` rejects any SAN that isn't a `DnsName`, requires the DNS SANs to equal the order's identifiers (else `BadCsr`), then **overwrites every extension the CSR asked for** before signing (`sanitize_csr_params`) — an empty subject, `is_ca = NoCa` (which omits `basicConstraints` entirely; `ExplicitNoCa` writes the `cA: FALSE` that is the ASN.1 DEFAULT, and certbot's `cryptography` rejects the chain over it), key usages, a fresh random serial, the AKI, `leaf_validity_days` validity, and the two pointer extensions from `LeafPolicy`. That reset matters: rcgen's CSR parser otherwise copies a requested `basicConstraints`/`keyUsage` straight into the signed leaf, so without it a client authorized for one name could submit a CSR carrying `CA:TRUE` + `keyCertSign` and receive a **working intermediate CA**. `revoke` records the serial in an in-memory ledger and regenerates the CRL (idempotent — a repeat is a no-op). The ledger's durable form is a JSON sidecar next to `crl_path` (extension swapped to `.json`), not the CRL's own DER round-tripped back. An empty, validly-signed CRL exists from construction, before any revocation ever happens. **Where its key lives is itself pluggable, through rcgen's own trait rather than one invented here**: `rcgen::SigningKey` is public and `Issuer<'a, S>`/`signed_by`/`self_signed` are all generic over it, so `LocalCa` holds an `Issuer<'static, CaSigningKey>` (`local_ca/key.rs`) — a `Software(KeyPair)` variant plus, behind `--features hsm`, a `Pkcs11` one — and `issue`/`revoke`/`crl_der` never name the key type. Two consequences: the issuer is behind an `Arc` and **both** signing calls (`csr.signed_by` in `issue`, `build_crl` in `revoke`) run under `spawn_blocking` *unconditionally* — `SigningKey::sign` is synchronous and called deep inside `signed_by`, so a token round trip would otherwise stall a runtime worker, and branching on the key kind is a correctness trap; and the key type must be `Send + Sync`, which is why `Pkcs11SigningKey` wraps cryptoki's `Send`-but-not-`Sync` `Session` in a `std::sync::Mutex` (the call never awaits, so an async mutex would buy nothing).

**Challenge subsystem** (`src/challenge/`): a trait, an error enum the *caller* maps to `Problem` (`challenge_problem` in `handlers/helpers.rs`), and a `from_config` selector that fails fast at startup. **Bypass is a flag on the registry, not a `NoopValidator`** — `from_config` must not *construct* the real validators when bypassing, since building them reads `/etc/resolv.conf` (or dials `dns.resolver`) and `TlsAlpn01Validator` builds a rustls `ClientConfig`; bypass is the default every test uses. `validate` wraps every attempt in `tokio::time::timeout` at the registry level. One shared `Arc<dyn Resolver>` (`dns.resolver` or system config, **uncached** — a client publishing a `dns-01` record moments before triggering would otherwise be defeated by a cached negative answer) is built once and passed to every validator that needs one; `filter::from_config` makes the same choice for `reverse_dns`.

- **`http_01.rs`** — GET the challenge path, body trimmed and compared to the key authorization. Behind an `HttpFetcher` trait; the production `hyper`-based impl deliberately doesn't add a `Host` header (a loopback test pins this).
- **`dns_01.rs`** — TXT at `_acme-challenge.<name>`, matching `base64url(SHA256(keyAuthorization))` — the digest, not the raw key authorization `http-01` serves. Matches *any* TXT record at the name, since a base+wildcard order publishes two.
- **`tls_alpn_01.rs`** — handshake with SNI = identifier, ALPN `acme-tls/1`. `verify_acme_identifier` requires exactly one matching `dNSName` SAN plus a **critical** `id-pe-acmeIdentifier` (`1.3.6.1.5.5.7.1.31`) extension holding the digest, compared with `subtle`'s constant-time equality.

**Two rustls constraints worth not rediscovering.** (1) The crypto provider is passed **explicitly** via `builder_with_provider`, never `CryptoProvider::install_default` (which panics on a second call and would make test ordering matter). (2) `AcceptAnyServerCert`'s signature-verification methods **assert rather than delegate** to `rustls::crypto::verify_tls*_signature` — those parse the peer certificate with `rustls-webpki`, which rejects an unrecognized **critical** extension, exactly what RFC 8737 requires `id-pe-acmeIdentifier` to be. Proven by the `tls_alpn_01::tests::loopback` test (`UnsupportedCriticalExtension`), whose server also has to resolve its certificate via `ResolvesServerCert` rather than `with_single_cert` for the same reason.

**http-01 redirects are an SSRF surface.** Following them is required by the spec, and Boulder's RFC1918-blocklist mitigation doesn't apply here — serving private networks is the point of this server. What keeps it contained: only `http`/`https`, only the two configured ports, at most `max_redirects` hops, the shared timeout, a `follow_redirects` off switch, and the fetched body is **never echoed into the client-visible error** (only its length; a truncated preview is logged at `debug`).

**Filter subsystem** (`src/filter/`): the `Check` trait (`kind`/`stages` plus two default-pass hooks), a three-valued `Verdict`, and a `from_config` that parses every CIDR, regex and condition at startup (a bad one is fatal) and warns when no rule is configured. `Outcome::Deny`/`Undecided` map to `access_denied`(403)/`server_internal`(500) at the middleware, `rejected_identifier`(403)/500 at `newOrder`, `bad_csr`(400)/500 at `finalize`. There is no `FilterError`: one type, mapped once, at each of the two call sites.

Four laws the evaluator rests on, each a bug if dropped:

1. **Kleene logic**, so an unknown propagates only when it could change the answer (`fail and unknown = fail`, `pass or unknown = pass`). Short-circuiting is structural in the evaluator, not in the combinators, because the hooks are `async` — and an `Undecided` left operand skips *nothing*, since the right operand is exactly what might rescue it.
2. **A rule's stages are the intersection of its checks'**, never the union: evaluating a rule where one check cannot run would substitute a silent `Pass`. An empty intersection is a startup error naming both sides.
3. **Each stage is evaluated independently and both must allow**, and **a stage with no applicable rules allows** without consulting `filter.default`.
4. **A rule whose condition came back `Undecided` is remembered, not skipped.** Once the policy reaches an answer, if that unknown rule's effect differs from the effect actually reached, the whole stage is `Undecided`. Without this, rule *order* would decide whether an outage is survivable.

Per-request **memoisation is mandatory, not an optimisation**: a check named twice runs once, because `custom` forks a process and `ipam` makes four HTTP requests.

- `ip_allow.rs`, `reverse_dns.rs` (PTR + optional forward confirmation + hostname regex, behind a `Resolver` trait with a timeout budget), and `identifiers.rs` (type then regex) all share `allow`/`deny` semantics via `filter::check_lists`: **`deny` wins**, checked first; an empty `allow` imposes no constraint (deny-only = a working blocklist); membership, not longest-prefix-match. `allowed_ip` errors at startup if both lists are empty (a pure no-op); the other two stay meaningful with empty lists. All fail closed on a missing client address (`ConnectionContext::require_client_ip()`), including in blocklist mode — an address the server can't see isn't "absent from deny, therefore fine". `reverse_dns` applies `deny` across **every** PTR candidate, not just the one that would otherwise be accepted.
- **CSR identifiers are typed and flattened** (`csr_identifiers`): SANs plus a subject `CommonName` all project into one `Identifier{typ, value}` list (`dns`/`ip`/`email`/`uri`/`other`/`cn`), so a deny rule can't be dodged by moving a name between them. `deny` reaches every type including `cn`; `allow` skips `cn` (`SUBJECT_ONLY_TYPES`) — a CN is legacy subject metadata and routinely a human label (rcgen defaults to `"rcgen self signed cert"`), not a name the certificate is *for*.
- Regex patterns are auto-anchored (`^(?:…)$`, case-insensitive) — the `regex` crate searches rather than matches, so an unanchored `example\.com` would also accept `example.com.evil.net`.
- **Client IP** (`client_ip.rs`): `ProxyPolicy::resolve` trusts the peer unless it's in `trusted_proxies`, then walks the forwarded-for list right-to-left past trusted hops. Addresses are canonicalized first (`IpAddr::to_canonical()`), since the dual-stack `[::]:3000` bind sees IPv4 clients as `::ffff:…`. Requires serving with `into_make_service_with_connect_info::<SocketAddr>()` or filters have no peer address at all and fail closed.

**HTTPS termination** (`src/tls.rs`): `from_config` returns `None` — touching no disk — when `server.tls.enabled` is off (the default). Otherwise it loads or generates+writes a self-signed cert for the `base_url` host, then reads back exactly what was written. The rustls `ServerConfig` passes the crypto provider explicitly (same rule as above) and advertises `http/1.1` only. `TlsListener` implements `axum::serve::Listener`:

- **Handshakes run off the accept path.** A background task accepts TCP and spawns each handshake under `handshake_timeout_ms` into a bounded channel `accept()` drains (the slot is reserved before accepting — both the backpressure and how a dropped listener stops the task). Doing the handshake inline would let one stalled client block every other connection for the length of the timeout.
- **`TlsListener::spawn` returns `HttpsListener = TapIo<TlsListener, …>`.** `into_make_service_with_connect_info::<SocketAddr>()` needs `SocketAddr: Connected<IncomingStream<'_, L>>`, which axum implements only for the concrete `TcpListener` and — blanket — any `TapIo<L, F>`. The missing impl can't be written here (foreign trait, foreign type — coherence refuses it), so `TapIo` is what carries the peer address into request extensions; without it, IP filters see no client address under TLS and fail closed.

### Module layout

- `src/main.rs` — thin binary entry point; excluded from the coverage floor (see CI).
- `src/cli/` — the `clap` command tree, plus `logging.rs` (`[logging]` → an installed subscriber; ~95 lines with no coupling to the rest of the file). **`run()` is the only place that prints an error and calls `std::process::exit`**: every command body returns `Result<(), CliError>` and `dispatch` routes to it, so each arm is a plain function a test can call and assert on rather than an unreachable dead end. `CliError` carries the message and has `From<sqlx::Error>` (`"database error: …"`), which is why the DB calls are plain `?`. `serve` binds `server.bind_address` and hands the socket to **`serve_on(config, database, listener, shutdown)`**, which runs `webadmin::check_config`, binds the admin socket when `[admin]` is enabled, and delegates to **`serve_on_with(…, admin_listener, …)`** — the split lets a test drive the two-listener path on two ephemeral ports. `serve_on_with` does everything else — profile resolution, deduplicated signer backends, per-profile filters/challenge validators, TLS, the `JobRegistry` assembled from `SignerBackend::jobs`, the job runner, the nonce reaper, the `Auditor` (built here rather than in `Profile::build_all`, because `[audit]` is process-wide and not a per-endpoint subsystem) and its retention sweep when `audit.retention_days` is non-zero, and `axum::serve` with `into_make_service_with_connect_info::<SocketAddr>()`. Splitting on the socket boundary is what lets a test drive the whole startup path on an ephemeral port with its own shutdown future instead of a process signal; only `run()`, `serve()`'s four-line shell and `shutdown_signal()` stay untested. (`serve_on`'s "register once per backend" list holds `usize`, not `*const ()` — a raw pointer held across an `.await` would make the future `!Send`, and it is spawned. The `watch::channel` carrying `shutdown` is created *before* profile assembly, so a signal arriving during startup is not ignored, and the job runner takes a receiver like both listeners.) The one `shutdown` future is split across both listeners through a `tokio::sync::watch`, with the relay task under `AbortOnDrop` so an error path does not leak a task parked on a signal that never arrives; both `axum::serve` futures are boxed (`type Serving`) because the TLS and cleartext arms have different listener types, and joined with `try_join!`. Logic beyond dispatch lives in `src/admin/`.
- `src/lib.rs` — library root: `Profile`, `AppState`, `build_router` (one profile) and `build_app` (root routes + one nested router per profile). Also installs the response-hardening layers (HSTS, `X-Content-Type-Options`, `X-Frame-Options`) and a `GlobalConcurrencyLimitLayer::new(100)` — note it *queues* rather than sheds, so it bounds concurrent work but doesn't reject a flood.
- `src/handlers/` — one file per ACME resource (`account.rs`, `authz.rs`, `certificate.rs`, `directory.rs`, `order.rs`, `renewal_info.rs`), re-exported flat from `mod.rs`; `helpers.rs` holds the shared ownership helpers, the filter-facing CSR projection, and the name-shape validators.
- `src/config/` — `mod.rs` (`Config::load`, `LIST_KEYS`, `empty_string_is_no_values`) and `types/` (the config structs, one file per TOML section: `server`/`signer`/`filter`/`challenge`/`notify`/`profile`, re-exported flat so no import outside the directory names a submodule).
- `src/audit/` — the audit vocabulary (`AuditEvent`, `Actor`/`ActorKind`, `AuditRecord`, `ClientContext`), the `RequestContext` extractor, the cached PTR resolver, and `write`/`Auditor::record`. Deliberately **not** merged into `src/notify/`, which fires at nearly the same call sites with nearly the same fields: a notification is outbound and lossy (a chat room, fire-and-forget), an audit row is inbound and durable and exists for the events nobody wants a notification about — the refusals. `write` is a free function as well as a method because the `relay` relay settles from a background task holding an `Arc<Database>` and no `Auditor`, and needs no resolver there (the address was resolved during the finalize request and parked on the `upstream_orders` row).
- `src/tls.rs`, `src/pemfile.rs`, `src/error.rs`, `src/cert.rs` — as described under Architecture above.
- `src/extractors/` — `acme.rs` (the `verify_jws` core + the two extractors), `jws.rs` (wire types), `signature.rs` (the cryptography: `verify_signature_and_get_der`, `verify_signature_with_spki`, `spki_parts`/`spki_to_jwk`, `jwk_thumbprint`, `SignatureError`).
- `src/eab.rs`, `src/key_change.rs` — pure verification, no database access; the DB lookup and active/revoked filtering happen in the handler.
- `src/signer/mod.rs`, `src/signer/local_ca/`, `src/signer/custom.rs` — as described under Architecture above. `local_ca/` is a directory since the key source became pluggable: `mod.rs` (issuance, and `impl LocalCa` whole — splitting an inherent impl across files costs more than the length does), `ca.rs` (generating the CA's own certificate and the serials it issues under), `crl.rs` (the revocation ledger and the CRL built from it — the two share only an `Issuer<'static, CaSigningKey>` with issuance), `key.rs` (`CaSigningKey`, `KeySource`, `read_pin` — always compiled), `policy.rs` (`LeafPolicy`: the two extensions naming this CA's own services, their URL validation and the hand-rolled AIA DER — everything that is decided once at startup rather than per issuance) and `pkcs11.rs` (`#[cfg(feature = "hsm")]`).
- `src/signer/relay/` — the relaying backend, split by concern: `mod.rs` (`ChallengeStrategy`, `PollConfig`, `Inner`, `RelaySigner`, `from_config`, the `SignerBackend` impl — whose `issue` opens the upstream order synchronously, then *enqueues* rather than spawning, and whose `jobs()` hands over the one `RelayJob`), `account.rs` (provisioning this proxy's own upstream account and the `kid` sidecar: the one part with a lifecycle of its own, run once and only *used* thereafter), `wire.rs` (all six upstream DTOs plus `parse_rfc3339`/`upstream_to_signer_error` — they had been scattered across three places), `flow.rs` (the background state machine: `RelayJob` — the `JobHandler` — plus `RelayFailure`/`classify`/`relay`/`answer_dns01`/`answer_http01`/`answer_bypass`/`poll_until`/`settle`, everything that runs *after* `issue` answered `processing`. `classify` is where an `UpstreamError` becomes retryable or permanent, table-tested one row per variant; `settle` returns the job's outcome rather than writing a failure itself, and `RelayJob::abandon` is the old `fail`), `client.rs` (a hand-written outbound ACME client), `testsrv.rs` (a `cfg(test)` scripted ACME server on loopback, so the client is tested against real HTTP without the network; with `Script::http01_responder` set it really *fetches* the challenge file before deciding the authorization, rather than just counting the trigger). The tests stay in this module — they enter through `SignerBackend::issue` and assert a *relay* outcome, so they follow the entry point rather than the assertion — but live in `tests/` beside it (`lifecycle`/`eab`/`dns01_strategy`/`http01_strategy`/`renewal`, fixtures in `tests/mod.rs`) rather than as one 2000-line inline block. `dns01.rs` is the one place that **writes** DNS: RFC 2136 + TSIG on `hickory-proto` (not `hickory-client`, whose 0.26 line is still pre-release). `http01.rs` is its twin, and the one place that **serves** a challenge file: a `TokenStore` seam over a `MemoryTokenStore`, plus a `PublishedToken` `Drop` guard — retraction can run from `Drop` here where the dns-01 side's network round trip cannot, which is what stops the runner's per-attempt timeout dropping the future mid-poll from leaking a live key authorization per timed-out relay. The key authorization at the upstream uses **this proxy's own thumbprint** for both, never the end client's — they're different accounts on different servers — and http-01 serves it *verbatim* where dns-01 publishes its SHA-256 digest (§8.3 vs §8.4). Two load-bearing gotchas: (1) `from_config` provisions on a scoped OS thread with its own runtime, since its caller (`cli::serve`) is already inside one and a plain `block_on` would panic; (2) unlike `challenge::tls_alpn_01`, this client **validates** the upstream's TLS certificate against `webpki-roots` — here the certificate is the only thing identifying the CA being handed CSRs.
- `src/challenge/mod.rs`, `http_01.rs`, `dns_01.rs`, `tls_alpn_01.rs` — as described under Architecture above.
- `src/dns.rs` — the shared `Resolver` trait + `HickoryResolver`, used by every DNS-touching consumer. `dns.resolver` now genuinely governs **every** outbound connection: `Profile::build_all` builds one uncached resolver and threads it through `signer`/`notify`/`filter`/`challenge`. `reverse_dns` deliberately keeps building its own **cached** resolver from `DnsConfig` — a PTR lookup for an address that keeps connecting is what a cache is for, while the shared one must stay uncached so a `dns-01` record published moments before a trigger is not defeated by a cached negative.
- `src/http_client.rs` — the transport half of the four outbound HTTP clients: `Endpoint::from_url` (host/scheme/port), `connect` (resolve → optional `CONNECT` tunnel → TLS → `http1::handshake` → detached connection task), `connect_stream` (the same minus HTTP, for `tls_alpn_01`'s raw probe) and `webpki_tls_config`. Deliberately **not** a shared client type: each caller keeps its own headers, body cap, error type and — the part that actually differs — its own TLS *choice*, since `challenge::http_01` must not validate the responder's certificate (RFC 8555 §8.3) while the other three must. `connect` returns a **`Connection<B>`**, not a bare `SendRequest`, because two things are properties of the *connection* rather than the caller: `request_target(&Url)` (absolute-form only when forwarding through a proxy, origin-form otherwise — so a request built for one shape is never sent on the other) and `send_request`, which attaches `Proxy-Authorization` and **never inside a tunnel**, where the credential was already spent on the `CONNECT` and repeating it would hand it to the origin. Three gotchas worth not rediscovering: `Endpoint::connect_authority()` always carries the port where `authority()` elides a default one (`CONNECT example.com` is malformed and every real proxy 400s it); the tunnel's `hyper::client::conn::http1::Connection::with_upgrades()` is load-bearing and its absence **hangs** rather than failing, which is why three loopback tests are shaped to time out; and the status is checked *before* `hyper::upgrade::on`, since a non-2xx has no upgrade to hand over and its body ("407 Proxy Authentication Required") is the whole diagnosis.
- `src/proxy.rs` — the policy half of the above: `OutboundProxies` (`from_config` with the environment fallback, `select`, `direct`), `ProxyTarget` and the `no_proxy` rules. Separate from `http_client` because that module's doc says it owns "the plumbing and nothing else", and this is a fallback precedence, six matching rules, a refusal vocabulary and a credential. `ProxyTarget`'s `Debug` is hand-written and `redacted()` is the only rendering of the URL that exists — every error and log line uses it, so a password never reaches a ticket. Reuses `filter::{parse_net, canonical}` rather than growing a second CIDR parser; that is stated in the module doc as a choice, with the hoist-to-a-neutral-module option named for whoever adds a third consumer.
- `src/filter/mod.rs`, `client_ip.rs`, `ip_allow.rs`, `path.rs`, `reverse_dns.rs`, `identifiers.rs`, `eab.rs` — as described under Architecture above. `path.rs` replaces `filter.exempt_paths` and exists for one concrete trap: **`/crl` is served by the profile router**, so an address-based policy without a path rule silently breaks revocation checking for every relying party outside the allowlist. Its `*` stops at `/` (one path segment), deliberately *not* sharing `glob_to_pattern` with the name checks, whose `*` stops at `.`. `eab.rs` matches the label of the credential an account registered under — the multi-tenant lever, and writeable in advance where an account id is not; it needs no migration, since `accounts.eab_kid` has recorded this since EAB was implemented, and it promotes that column from "audit trail only" to a policy input.
- `src/filter/policy.rs`, `expr.rs`, `build.rs`, `explain.rs` — the engine. `policy.rs` holds `Check`/`Verdict`/`StageSet`/`FilterPolicy` and the evaluator; `expr.rs` the condition parser (hand-written recursive descent, column-bearing errors, a `Display` that re-prints with explicit parens — which is what `filter show` prints); `build.rs` the config→policy resolver, **the only place that knows which flattened key belongs to which type**, and where every startup refusal is worded; `explain.rs` everything the two CLI commands print.
- `src/filter/ipam.rs` — the `ipam` check, the `src/ipam/` subsystem's only consumer. A **second** `ipam` check in one profile is a startup error: a profile has exactly one inventory, the one `[ipam]` configures. Identifier hook only (a connection hook would query the inventory on every `newNonce`). Holds nothing but an `Arc<IpamRegistry>` and interpolates `backend_name()` into every refusal, so a phpIPAM operator reads "phpIPAM" in the 403. Matching is exact (case/trailing-dot-insensitive, otherwise literal — `*.example.com` needs that exact string).
- `src/ipam/` — the inventory subsystem. `mod.rs` (`Ipam`, `AddressNames`, `IpamError`, `Source`/`parse_sources`, `IpamRegistry` and its budget, `from_config`, plus the shared `normalize`/`field_values`/`value_kind`), `http.rs` (the JSON-over-HTTP transport **both** backends share — the one case `http_client`'s "policy stays per-module" rule does not cover, since these two have the same policy; `JsonApiError` carries the status because that is the only thing that differs), `netbox/{mod,client}.rs` and `phpipam/{mod,client}.rs`. Each backend keeps a trait seam over its own queries (`NetboxApi`/`PhpIpamApi`) so the policy is testable without a server, the same shape `crate::dns::Resolver` gives `reverse_dns`.
- `src/jobs/` — the durable queue. `mod.rs` (`JobOutcome`, `JobHandler`, `JobSpec`, `JobQueue` — the enqueue side plus the runner's `Notify`), `registry.rs` (`JobRegistry`; a duplicate `kind` is a startup error, since two handlers would each claim about half the rows), `runner.rs` (`spawn_runner`, the claim loop, `backoff`, the graceful stop) and `retention.rs` (the queue's own sweep, and the `Reschedule` example). The model is `src/sqlite/job.rs`. **No `#[instrument]` anywhere in this module**, the rule `src/webadmin/` keeps and for both of its reasons. Two ordering traps are documented at their call sites: the concurrency permit is acquired **before** the claim (claiming first would start every backlogged row's lease ticking while it queued, and each would then be reclaimed as "crashed" having never run), and `abandon` is called only *after* the settling write took, so a runner whose lease was reclaimed does not tell a subject its work failed while another runner is still doing it.

- `src/script_hook.rs` — the contract all three `custom` hooks run under, in one place: `ScriptHook::new/run/detail`, `ScriptStdin::{Null,Json}`, `ScriptError`, `ScriptOutcome`. Owns the hardening (`env_clear()`, minimal `PATH`, `kill_on_drop(true)`, `tokio::time::timeout`) that used to be written out three times token-for-token. Each subsystem keeps only what is genuinely its own — its env vars, its stdout parsing, its error mapping, `signer`'s reserved exit code 3, `filter`'s `Denied`-on-nonzero, `filter`'s `pass_stdin`. `ScriptOutcome::stdin_error` records an `EPIPE` on the stdin write and surfaces it through `detail()` *only when the script also failed*, so "the script never saw the CSR" stops reading like "the script rejected the CSR" without breaking a script that legitimately ignores its payload.
- `src/testutil.rs` (`#[cfg(test)]`) — `TempDir` (which implements `AsRef<Path>`, so it drops into anything taking a path), `write_script`, `identifiers`/`dns_identifiers`, and `account_id`. Each of them had grown copies across the crate — seven of `TempDir`, three of `account_id`, and twelve hand-rolled `Identifier` builders before `Identifier::dns`/`::new` went into production where they belong. `tests/common/mod.rs` carries a second copy of the directory helpers, because an integration test cannot see a `#[cfg(test)]` item of the crate it links against.
- `src/filter/custom.rs` — the `custom` check (`CustomScriptFilter`): runs an operator-supplied script at both hooks, context via `ACME_FILTER_*` env vars and optional stdin JSON; exit 0 permits. `ACME_FILTER_CHECK_NAME` tells it which instance invoked it, so one script can serve several. The child runs with `env_clear()` (this process's own environment holds secrets, e.g. the RFC 2136 TSIG key) plus a minimal `PATH`, and `kill_on_drop(true)` (a `tokio::time::timeout` only drops the future, so without this a timed-out script would outlive its deadline and leak a process per request).
- `src/middlewares/filter.rs` — the connection-filter layer; inserts `ClientIp` into request extensions.
- `src/middlewares/nonce.rs` — the `Replay-Nonce` response middleware.
- `src/middlewares/index_link.rs` — the `Link: <…/directory>;rel="index"` response middleware (§7.1, on every resource but the directory). **Appends**, never sets: `post_challenge`'s `rel="up"` has to survive alongside it.
- `src/middlewares/access.rs` — request correlation *and* the access line, in one server-wide layer (was `request_id.rs` plus a per-profile `TraceLayer`). Reads or generates `x-request-id`, opens the `request` span every other line of that request nests under, and emits one `request_completed` carrying `status`/`latency_ms`. Three things the split got wrong and this fixes: `Span::current().record("request_id", …)` ran before `TraceLayer` had created a span and wrote to nothing; the root routes (`/health`, `/`, the http-01 responder) and the admission layer sat outside the profile routers, so `request_shed`/`request_deadline_exceeded` carried no id; and `DefaultOnResponse` emits under the `tower_http` target, which the shipped filter set to `warn`, so the access line was configured at INFO and silenced. Hand-written rather than `TraceLayer` because `on_response` never sees the request and so cannot drop `/health` to `debug`. The span declares `profile` as `field::Empty`; `build_router`'s outermost layer records it, which is the deferred-record pattern done correctly — the same one `verify_jws` now declares `alg`/`account_id` for.
- `src/sqlite/db.rs` — connection + automatic migration runner.
- `src/sqlite/nonce.rs`, `account.rs`, `order.rs`, `authz.rs`, `eab.rs` — the models described under Architecture above; DB methods return `Result<_, sqlx::Error>`.
- `src/sqlite/audit.rs` — `AuditEntry`/`AuditQuery`: append, read back, page, purge by age. No setter, no `UPDATE`. `event`/`actor_kind` come back as the **strings** they were stored as rather than as enums, so an older build reading a newer database renders an unrecognised event instead of refusing to load; `AuditEntry::event()` parses for the callers that want the enum.
- `src/cli/audit.rs` — the `audit list|show|cleanup` clap tree.
- `src/cli/filter.rs` — the `filter show|explain` clap tree, argument marshalling only. `resolve_profile` lives in `src/cli/mod.rs` (hoisted when this became its second caller).
- `src/webadmin/handlers/audit.rs`, `src/webadmin/pages/audit.rs` — the JSON and HTML surfaces. **Read-only by design**, which is why neither appears in `mutating_endpoints()`/`mutating_page_endpoints()`: there is no route to list.
- `src/sqlite/upstream_order.rs` — maps a local order to the order the `relay` backend opened for it upstream. `order_id` as the primary key doubles as the concurrency guard: two finalize requests racing on one order can't both open an upstream order, since the second insert conflicts.
- `src/admin/` — the operation layer **both front ends dispatch to and neither owns**: `src/cli/` and `src/webadmin/` are the two. `prompt.rs` (`confirm`, over an injectable `BufRead`), `ops.rs` (the operations), `render.rs` (`render_*`, human line or JSON; order rendering additionally surfaces `revokedAt`/`revocationReason`, admin-only visibility since `Order::to_json` carries no such fields), `password.rs`, `users.rs`, and the second factor: `totp.rs` (RFC 6238 over RFC 4226 on `ring::hmac`, plus the base32 *encoder* — nothing ever decodes it, so there is deliberately no decoder), `recovery.rs` (generation and normalisation) and `mfa.rs` (where those two meet a database).
  - `revoke_order` takes an `Actor` and a `ClientContext` from its caller rather than deriving them: this layer is front-end agnostic, so the CLI supplies `Actor::cli` with an empty context (there was no request, and the row says so) and the web admin supplies `Actor::admin(username)` with the operator's own address — **the operator, not the certificate's owner**, since an administrative revocation attributed to the client would say the opposite of what happened. Its four non-revoking outcomes write no audit row: the operator is being told the state of things, unlike `POST /revokeCert`'s refusals, which are a remote party being turned away.
  - **Each destructive op comes in two forms**: a bare `delete_account(id, db)` / `delete_order` / `cleanup_nonces`, and a `confirm_*` wrapper taking `assume_yes` + `reader`. The CLI calls the wrapper; the web calls the bare one. Before the split an HTTP caller had to pass `true` and an empty reader, asserting a confirmation that never happened — and the `impl BufRead` generic made the function non-object-safe for no benefit on that path. The bare deletes return `Option<Deleted { cascaded }>`, since the count is already computed for the prompt. `revoke_order` was never confirm-gated (revocation only tightens trust).
  - `password.rs` — PBKDF2-HMAC-SHA256 via `ring::pbkdf2`, 600 000 iterations, stored `pbkdf2-sha256$<iters>$<salt>$<hash>` (self-describing, so raising the cost or swapping to Argon2id is one branch plus rehash-on-login, never a migration). Deliberately **not** `argon2`: four crates into a CA's dependency graph — all re-audited by `cargo deny` at `all-features = true` — for a subsystem that is off by default and whose password is the bootstrap credential in a design that ends in a second factor. ~85 ms per hash in release, ~1.3 s in debug, which is why only two tests use the real constants and the rest go through the private `hash_with_iterations`.
  - `users.rs` — `create_user`/`set_password`/`set_status`/`delete_user`/`revoke_sessions`/`authenticate`. `authenticate` runs the KDF **even for an unknown username** (against `password::dummy_hash`), or login latency enumerates the operator table, and returns a four-variant `AuthOutcome` the caller collapses into one `invalid_credentials` *for the client* while logging which actually happened.
- `src/webadmin/` — the HTTP front end. `mod.rs` (`AdminState`, `build_admin_app`, `check_config` — `AdminState` holds the **same** `Arc<Auditor>` the ACME listener does, so an operator revoking through the panel writes into the one trail), `error.rs` (`AdminError`, `application/json`, stable snake_case codes — **never** `Problem`, whose every `typ` is a hardcoded ACME URN), `session.rs` (token mint/hash, the `__Host-` cookie, **five** extractors, the CSRF + origin gates, `LoginLimiter`, `spawn_session_reaper`, `AdminClientIp`, `PENDING_MFA_TTL`), `handlers/` (one file per resource, flat re-exports, plus `paging.rs`).
  - **CSRF enforcement is structural, not a layer**: `AuthenticatedWrite` is the only way a mutating handler can reach a session, and constructing it runs the check — the same reasoning that hoisted the media-type/`crit`/`url`/nonce checks into `AcmeRequest`. The residual risk (a new handler taking `Authenticated` by mistake) is closed by the table-driven suite in `tests/admin_api.rs`; **an endpoint missing from `mutating_endpoints()` is a review catch**.
  - **The two MFA-step routes are the one exemption**, and it is deliberate: `POST /api/session/mfa` and `POST /ui/login/mfa` run the origin gate and **no CSRF check**, because the challenge page is a plain form (sign-in must work with JavaScript off, which `tests/admin_pages.rs` pins for `login.html`) and `check_csrf` reads a header a form cannot set. `POST /ui/login` already makes exactly this trade one step earlier. Teaching `check_csrf` to also read a form field would be a second CSRF path, which is what `pages/auth.rs`'s shape exists to prevent. They live in their own `mfa_step_endpoints()` table with their own tests, so the exclusion reads as a decision rather than a gap.
  - **Three extractors carry the second factor**: `PendingMfa` (a live session that is *not* active — `resolve_session`'s exact mirror image, over a shared `resolve_live` that judges liveness and never `state`), `PendingMfaSubmit` (that, plus the origin gate), and `EnrolWrite` (an `active` session, **or** a `pending_mfa` one **only when `!user.has_totp()`**). That last condition is the whole security of the type: a session that owes a *code* must never reach an enrolment route, or the factor is bypassable by enrolling a new one over it.
  - `SameSite=Strict` is set but is **not sufficient alone**, for a reason worth not rediscovering: SameSite is scoped to the registrable domain, not the origin — *different ports of the same host are same-site*, which is exactly this deployment. Hence the per-session token, plus an origin gate that also covers login (which carries no session yet).
  - `AdminState` is not `AppState`: the latter holds exactly one `Profile`, and this listener is cross-profile (revoking an order resolves **that order's own** profile's signer, or answers `409 profile_not_mounted`). `build_admin_app` takes `&[Arc<Profile>]` as a **slice** so it must be called before `build_app` consumes the `Vec` — the ordering is stated in the signature rather than rediscovered as a borrow error.
  - **No `#[instrument]` anywhere in this module** — a rule, not a preference: the access middleware already opens the request span, and the attribute tanks reported coverage (see the Coverage gotcha).
- `src/webadmin/pages/` — the HTML front end at `/ui`, the sibling of `handlers/` and built the same way (one file per resource, doc comment starting with the literal route, `not_found` per file, no `#[instrument]`). `mod.rs` (`pages_router`, plus `chrome`/`respond`/`respond_fragment`/`flash`/`flash_error`/`pager`), `templates.rs` (`EMBEDDED_TEMPLATES` + `build_environment` + `render`, a deliberate copy of `notify::build_environment`), `error.rs` (`PageError`, `redirect`, `escape_html`), `auth.rs` (`PageSession`/`PageSessionWrite`/`PageMfaPending`/`PageMfaSubmit`/`PageEnrolWrite`/`is_htmx`), `assets.rs`, and `{session,account,accounts,orders,eab,misc}.rs`. Templates in `src/webadmin/templates/*.html`, assets in `src/webadmin/static/`. `mfa/` and `account/` hold the second factor's five: `mfa/challenge.html` is standalone like `login.html` and branches on `step`; `mfa/_setup.html` is included from both the sign-in flow (a plain form) and the account page (htmx), so it renders no form element of its own; `account/_mfa.html` is the swap target and `account/_card.html` the card inside it, split so `account/_codes.html` can show a fresh set *and* the up-to-date card without nesting two elements carrying one `id`.
  - **`.html`, never `.j2`, is a security control**: minijinja picks auto-escaping off the template *name*, and the notify templates are `.j2` precisely so escaping is off for them. A page template renamed `.j2` turns an account contact or an EAB label into stored XSS. `auto_escaping_is_on_for_pages_and_off_for_notify` pins both directions.
  - **`PageError` is separate from `AdminError`** because the latter's `IntoResponse` is JSON-only, and a browser needs to *arrive* at `/ui/login`. Its shape is fixed at construction, not in `into_response`: a `303` cannot serve htmx, since `fetch` follows the redirect before htmx sees a header and the sign-in page would be swapped into the clicked element — so the extractors read `HX-Request` from `parts.headers` and pick `303 + Location` or `204 + HX-Redirect`. It renders **no template** (a `const` document plus a local `escape_html`), the same reasoning that keeps `AdminError`'s body a `json!` literal.
  - **`PageSessionWrite` wraps `AuthenticatedWrite`**, so the origin/session/CSRF gates stay one implementation. The token reaches the browser as `hx-headers` on `<body>` in `layout.html` and returns as `X-CSRF-Token`, which is why `check_csrf` needed no second path and why htmx was chosen over plain forms. `tests/admin_pages.rs::mutating_page_endpoints()` is the `/ui` twin of the API's table — **a `/ui` route added and not added there is a review catch**.
  - Two htmx settings in `layout.html` are load-bearing and documented in `src/webadmin/static/README.md`: `includeIndicatorStyles: false` (htmx would otherwise inject an inline `<style>` the CSP blocks; the rules live in `admin.css`) and `responseHandling` (htmx does not swap non-2xx by default, so a `409` would fail silently instead of showing a banner). The refusal split is "the row's state is a banner, the server's problem is a page".
  - `htmx.min.js` is vendored (2.0.10, `0BSD`). `cargo deny` audits crates and cannot see it, so `src/webadmin/static/README.md` — version, URL, SHA-256, licence, refresh command — is the only provenance record.
- `src/sqlite/admin_user.rs`, `admin_session.rs`, `admin_recovery_code.rs` — the three models above. The session layer **never sees the plaintext token**; it arrives already hashed from `webadmin::session`, which is also why there is no `find_by_id` (the hash *is* the lookup key).
- `src/cli/webadmin.rs` — the `admin user`/`admin session`/`admin user totp` clap tree.

## Conventions & gotchas

- **URLs derive from `config.server.base_url`** in `get_directory` and the extractor's JWS `url` check — never hardcode one. `tests/config_driven.rs` runs the whole flow against a non-default `base_url` to catch a regression. `get_directory` advertises only routed endpoints (`newNonce`/`newAccount`/`newOrder`/`revokeCert`/`keyChange`/`renewalInfo`) plus whichever `meta` members are configured (`externalAccountRequired` when EAB is on, and `termsOfService`/`website`/`caaIdentities` from `[meta]`) — an unset one is omitted, never sent empty; `renewalInfo` advertises the base URL without an id, since RFC 9773 §4.1 has the client append it. `GET /crl` is routed but deliberately not advertised — it's CA infrastructure, not an ACME resource.
- **Handlers reject invalid input with `Problem`** (`src/error.rs`). The media-type/`crit`/`url`/nonce checks happen in the extractor (see Architecture step 2), so a new handler taking `AcmeRequest<T>`/`AcmePostAsGet`/`AcmeOptionalPayload<T>` doesn't need to repeat them. A handler needing a dynamic status/header returns `Result<Response, Problem>` built via `(...).into_response()` — that is how `post_key_change`'s `409` gets its `Location` and `post_new_account`'s `userActionRequired` its `Link`. Every constructor funnels through a private `Problem::build`, and the three optional members (`identifier`, `subproblems`, type-specific extras like `badSignatureAlgorithm`'s `algorithms`) live behind an `Option<Box<_>>`: `Problem` is the `Err` of nearly every function here, so inlining them pushed it past clippy's `result_large_err` threshold. `identifier` renders **only** inside `subproblems` — §6.7.1 forbids it at the top level, and `to_value` enforces that rather than trusting call sites.
- **Error handling splits by phase**: startup paths (DB connect, migrations) may still `panic!`/`unwrap` to fail fast; request-path DB calls return `Result` and degrade — the nonce middleware logs and drops `Replay-Nonce` on a save failure, and handlers turn DB errors into 500 `Problem`s instead of panicking.
- **Logging convention** — nine rules, and **`tests/logging_convention.rs` enforces all of them** by walking `src/` and extracting every one of the ~468 call sites. That test exists because the prose version of these rules rotted: an audit found two sites computing `event`, ~24 names with no subsystem prefix, nine concepts spelled two ways (three inside a single file), and `payload_length` meaning base64 characters at one call site and decoded bytes eight lines below. **Read the test before adding a call site**; its failure messages name the rule.
  1. `event` is the **first** field and always a **bare string literal** — never a variable, `if`/`else` or `format!`, so a name in a log greps straight back to the line that wrote it. The single exemption is `pemfile::warn_if_key_is_readable`, which takes the name as a `&'static str` so four subsystems share one warning; every caller passes `<subsystem>_key_permissive`.
  2. Shape is `<subsystem>_<object>_<outcome>`, snake_case, **outcome in past tense**. No gerunds, no adjective-first (`malformed_identifier`), no verb-first (`revoke_cert_*`).
  3. The subsystem prefix comes from a **closed list** (`SUBSYSTEMS` in the test). A family grep has to find the whole family.
  4. Challenge-type tokens are always separated: `http_01`, `dns_01`, `tls_alpn_01`.
  5. **One name means one thing.** Where two front ends or three operations would share a name they keep it and add a discriminating field — `surface = "api"|"ui"` across `webadmin/handlers/` and `webadmin/pages/`, `scope = "user"|"user_except_current"|"all"` on `db_admin_sessions_revoked`.
  6. **`db_` marks the storage layer**: every event emitted from `src/sqlite/` carries it, enforced off the file path. Level stays orthogonal — the prefix is the layer, the level is the importance.
  7. Every site carries **`outcome = "success"|"failure"|"progress"|"advisory"`** directly after `event`. This is `audit_log.outcome` applied to the log stream, and for the same reason: failure is spelled a dozen ways across ~450 names, so `event LIKE '%_failed'` misses most of it. `progress` is a `_started`/`_requested` line whose result is not yet known; `advisory` is `warn` where nothing failed (`tls_disabled`, `challenge_validation_bypassed`). Every `error!` is `failure`.
  8. **One name emits at one level.** The sole exemption is `request_completed`, which varies by response status and is documented as a table.
  9. A numeric field carries its unit: `_ms`, `_bytes`, `_b64_chars`, `_seconds`, `_days`; a delete count is `rows_removed`; a fingerprint is `<thing>_fp`. **A duration goes through `acme_proxy::millis`**, never `Duration::as_millis()` — the latter is `u128`, which `tracing` records via `Display` and lands in the JSON output as `"42"` rather than `42`.

  `doc/src/operations/monitoring.md` is the operator-facing catalogue and a **curated subset**; the guard checks one-directionally that everything it names is still emitted, so a rename that misses the page fails CI. Event names asserted by `tests/e2e/` are grep-before-renaming, and `server_startup` is a container *readiness gate*, so changing it fails as a start timeout rather than an assertion.
- Shared state is `AppState { database: Arc<Database>, config: Arc<Config>, profile: Arc<Profile>, audit: Arc<Auditor> }`, injected via a single `State<AppState>` (two separate `State<Arc<…>>` extractors trips axum's state-type inference). The nonce middleware keeps its own `Arc<Database>` state independently via `from_fn_with_state`.
- **`#[instrument]` is banned in `src/webadmin/`** — a rule for that module, not a preference. The access middleware already opens the request span, so it would buy nothing, and the attribute moves a handler body into a generated async block that reports almost no coverage.
- Comments, doc comments and error-message strings are **in English**. (This rule said "in French" long after the last French had gone, which was actively inviting new French into files that had none. The two survivors — both in `src/handlers/helpers.rs`'s `#[cfg(test)]` module — have since been translated, and `src/` is now clean.)
- **`anyhow` is used in 20 files and `.context()` is never called** — every error is built with `anyhow!("… {error}")`, which is what makes `cli/mod.rs`'s `CliError(error.to_string())` lossless. A future `.context()` would silently start truncating startup errors at that line.
- Edition is **2024**.
